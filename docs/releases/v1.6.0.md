# v1.6.0 — Alignment with ProcurAuth 1.1

Base: release 1.5.1. This release follows the rulings of the owner on the alignment of ChDash with ProcurAuth. These rulings are the decisions 188, 195 and 203 to 213 of ProcurAuth, and the rulings of 2026-11-23. It follows the release 1.1 of ProcurAuth. It has breaking changes: read the section "Upgrade".

## What changed

- **An `evaluation_id` above 1024 bytes makes the answer of the PDP not valid** (ProcurAuth 17.1, decision 188). Before, ChDash accepted 4096 bytes and dropped a longer id: the call got a plain refusal. Now a route answers `503`, and an MCP call gets HTTP 503 with `-32603`.
- **A ceiling above 2^53-1 in `context.limits` makes the answer not valid** (ProcurAuth 6, decision 188). Before, ChDash accepted each whole number up to 2^64-1.
- **A reason of 17.1 for a question with `context.permission_only` makes the answer not valid** (ProcurAuth 5.5a and 10.3, MCP binding 3.7, decision 195). The PDP client applies the rule to each question of this kind. The route of an export answers `503`, not `403` with `approval_cannot_wait`. The tool `export_query` gets HTTP 503 with `-32603`. ChDash no longer has the tool error `scope_needs_approval`.
- **The other run action has `context.permission_only`.** A run asks the action of its use with `context.usage`, then the other run action to know `readonly` and the ceilings of the other class. This second question now has `context.permission_only` equal to `true` (ProcurAuth 5.5a). The PDP thus ignores `confirm` for it: a grant of `query.run.write` with `confirm` no longer gives `readonly = 1` to a read.
- **ChDash refuses a token without `kid` when the configuration has more than one key** (ProcurAuth 9.4). The reason in the log is `kid`. Before, ChDash tried each key. With one key, ChDash still verifies a token without `kid` with this key.
- **`iat`, `exp` and `nbf` are whole numbers written with digits only.** A fraction, an exponent and a sign give `401` (the reason `malformed`). Before, ChDash accepted a number with a fraction up to 9e15 and rounded it down. ChDash still refuses a token when `nbf` is later than its clock plus `identity.clock_skew`.
- **A route that runs no action asks `access` on the service** (ProcurAuth 10.0 step 2 and 10.1c, decision 210). The health probes `/livez`, `/readyz` and `/healthz` still need no token and ask nothing. Each other route needs the identity token: `/metrics` too, which needed nothing before. The routes that run no action ask the action `access` on the resource `service`, with no usage and no approval. Before, they needed the token only.

  These routes are the shells of the pages, the files of `/static/`, the redirects, `/metrics`, `GET /api/version`, `GET /api/hosts`, `GET /api/hosts/stream`, `GET /api/health`, `GET /api/mcp/meta` and the two cancel routes. A refusal gives `403` with the action `access` (the HTML `403` page for the address of a page), and no valid answer gives `503`. A reason of 17.1 for `access` is not a valid answer (`503`).

  The answer has no usage, so the cache of the PDP client keeps it for `pdp.cache_ttl`. Thus the files of a page cost one question to the PDP for each subject and each period. The mode `open` does not change. The mode `keys` of `/mcp` does not change.
- **The metadata member `procurauth_directory_max_age_seconds`** (ProcurAuth 3.9 and 10.7b, decision 208). ChDash reads it as it reads the members `procurauth_approval_*`: a value that is not a whole number from 1 is ignored. The start writes it in the line `access.pdp_metadata` (`directory_max_age_seconds`, `0` when it is absent). ChDash takes no decision from it.
- **A key of the configuration file asks the PDP in the mode `authzen`.** The owner decided on 2026-11-23 that the use of such a key can need an approval. An `mcp_key` block, or a `key` block of the older form, of the mode `keys` asks the PDP with the subject `key:<name>` (ProcurAuth 3.2). The rules of a key of the page apply with this subject in place of the creator. They are the state of the key, the questions of a call, the budget `queries` and the flow of an approval. A key applies no ceiling, so a ceiling refuses the call.

  `tools/list` gives such a key the control arguments and `get_action_status`. The answer `unknown_subject` refuses each tool of an action (`-32602`), and the key is never an orphan. A ceiling gives HTTP `403` with `-32001` and the message `forbidden: the grant of this key has a limit that a key cannot apply. Use the identity mode of MCP`. Before, such a key asked the PDP nothing. The mode `open` has no PDP: there, such a key works as before.

## Upgrade

- An edge that signs with one of several keys must put `kid` in each token. For a PEM key, the `kid` is its RFC 7638 thumbprint, which `--print-config` shows. The portal puts `kid` in each token.
- An edge must write `iat`, `exp` and `nbf` as whole numbers.
- A PDP must not give a reason of 17.1 to a question with `context.permission_only`, and must give an `evaluation_id` of 1024 bytes at most.
- In the mode `authzen`, Prometheus reads `/metrics` through the edge, with a key that holds `access` on the service. The platform keeps the health probes `/livez`, `/readyz` and `/healthz`, which need no token.
- The PDP must give `access` on the service to each subject that uses the pages: the portal does. A PDP that refuses `access` now refuses the files of the pages too.
- In the mode `authzen`, make a key in the PDP for each key of the configuration file. Its id is the name of the block. Give it its grants. Until then, each tool of an action of that key is refused (`-32602`). The tools with no action (`list_hosts`, `mcp_analysis_my_limits`, `mcp_analysis_my_usage`) continue to work.
