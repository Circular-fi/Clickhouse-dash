# v44 — Pipeline correctness and bounded matching

## Base and application

This change is based on the exact uploaded `Clickhouse-dash(7).zip` snapshot.
All 74 files in the supplied v43 patch already match that snapshot. The v41,
v42 and v43 patches must not be reapplied on top of this delivery.

Apply the incremental patch from the **Clickhouse-dash repository root**:

```bash
git apply --check /path/to/Clickhouse-dash-v43-to-v44.patch
git apply /path/to/Clickhouse-dash-v43-to-v44.patch
```

The full source archive is the alternative for a fresh source directory. It
contains the existing project plus this change; it omits Git history and local
build/cache files. Rebuild the application to include its embedded browser assets.
No database migration is required.

## Changes

- Processor identities and graph edges are scoped by host and native query ID.
  IDs, parent IDs, plan steps and plan groups use decimal strings on the wire,
  preserving all UInt64 bits. Safe numeric IDs from older exports still work.
- Trace ownership uses query IDs exposed by summary/root spans, rather than the
  chronological position of a trace. Missing traces cannot shift retry ownership.
- Input/output counters are summed at stage boundaries, including parallel lanes
  and excluding internal sequential processors. Incomplete or mixed boundaries
  are labeled approximate. Waiting-only stages remain visible.
- Matching uses indexed cost buckets, disjoint sets and a stage-range index.
  Equal or near-equal candidates across different stages stay unassigned; accepted
  counter-based associations are labeled estimated. Unmatched trace instances
  are not forced onto the busiest stage.
- Full-summary Pipeline collection is attempted independently of detailed Tracing
  success. Per-family detail fallback remains possible when other families have
  summary data. Full-trace timing envelopes remain independent of the detailed
  span cap and are explicitly described as including possible idle gaps.
- Independent processor and summary truncation flags, availability and errors
  reach the UI and debug archive. Existing query bounds and the 4K trace format
  remain in use.
- The time ruler and rows share horizontal scrolling; the ruler stays visible
  vertically. Tiny events at the right edge retain two visible pixels. Bars have
  stronger contrast in both themes; flow counts and byte sizes use separate lines.
- CMake tracks edits, additions and removals under `src/static`, so incremental
  builds regenerate embedded assets instead of serving stale JavaScript or CSS.
- Profiling documentation and the English debug-archive README describe the
  current data contract and distinguish active work, waits and wall-clock time.

### Local model benchmark

A deterministic same-family fixture measured `buildModel` only, excluding SQL,
network transfer and DOM rendering. These are single local runs, not production
latency guarantees:

| Processors and summaries | Uploaded model | Updated model |
| --- | ---: | ---: |
| 1,000 | 471 ms | 41 ms |
| 10,000 | 43,878 ms | 287 ms |

This fixture deliberately uses closely spaced costs across distinct stages. The
new model keeps those associations ambiguous, while the old model assigned all
of them. It therefore measures both the indexed algorithm and the intentional
change in ambiguity handling, not strict output-equivalent throughput.

## Compatibility and remaining limits

External consumers of `/api/query/analysis` must accept strings for processor
identity fields. Counter and timestamp fields retain their existing types.
Only query IDs actually present in the logs can identify traces; old multi-attempt
archives without those IDs may show timings without stage attribution. A summary
bar is an envelope, and cost-based association remains a heuristic even when its
threshold passes. Per-port counts and missing/truncated processor data cannot be
reconstructed. System logs remain scoped to the configured local replica.

Details: [Query analysis](../query-analysis.md).
