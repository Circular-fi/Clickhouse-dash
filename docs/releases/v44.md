## Changes

- This change scopes processor identities and graph edges by host and native query ID. IDs, parent IDs, plan steps and plan groups use decimal strings on the wire. This keeps all UInt64 bits. Safe numeric IDs from older exports still work.
- Trace ownership uses the query IDs that summary and root spans expose, not the chronological position of a trace. A missing trace cannot shift retry ownership.
- This change sums the input/output counters at stage boundaries. It includes parallel lanes and excludes internal sequential processors. The change labels incomplete or mixed boundaries as approximate. Stages that only wait stay visible.
- The matching step uses indexed cost buckets, disjoint sets and a stage-range index. Candidates that are equal or nearly equal across different stages stay unassigned. The application labels accepted counter-based associations as estimated. The model does not force unmatched trace instances onto the busiest stage.
- This change attempts full-summary Pipeline collection separately from detailed Tracing success. A per-family detail fallback is still possible when other families have summary data. Full-trace timing envelopes do not depend on the detailed span cap. The text explicitly describes them as containing possible idle gaps.
- Separate processor and summary truncation flags, availability and errors reach the UI and the debug archive. The application still uses the current query bounds and the 4K trace format.
- The time ruler and the rows share one horizontal scroll. The ruler stays visible when the page scrolls vertically. Tiny events at the right edge keep two visible pixels. Bars have stronger contrast in both themes. Flow counts and byte sizes use separate lines.
- CMake tracks edits, additions and removals under `src/static`. Incremental builds regenerate embedded assets. The builds do not serve stale JavaScript or CSS.
- The profiling documentation and the English debug-archive README describe the current data contract. They distinguish active work, waits and wall-clock time.

### Local model benchmark

A deterministic same-family fixture measured `buildModel` only. The measurement did not include SQL, network transfer or DOM rendering. These are single local runs, not production latency guarantees:

| Processors and summaries | Uploaded model | Updated model |
| --- | ---: | ---: |
| 1,000 | 471 ms | 41 ms |
| 10,000 | 43,878 ms | 287 ms |

This fixture deliberately uses closely spaced costs across distinct stages. The new model keeps those associations ambiguous. The old model assigned all of them. The benchmark therefore measures two things: the indexed algorithm and the intentional change in ambiguity handling. It does not measure strict output-equivalent throughput.

## Compatibility and remaining limits

External consumers of `/api/query/analysis` must accept strings for processor identity fields. Counter and timestamp fields keep their current types.

Only query IDs that are present in the logs can identify traces. Old multi-attempt archives without those IDs may show timings without stage attribution. A summary bar is an envelope. Cost-based association is still a heuristic, even when its threshold passes. The application cannot reconstruct per-port counts or processor data that is missing or truncated. System logs still apply only to the configured local replica.
