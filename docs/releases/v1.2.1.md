# v1.2.1 — TLS to ClickHouse

Base: release 1.2.0. This release adds a TLS client for the native protocol of ClickHouse. A URI with `secure=1` now connects with TLS. Before, the release binaries refused it.

## What is new

- The release binaries contain OpenSSL 3.5.9 as static libraries (Linux amd64 and arm64 with musl, macOS amd64 and arm64). The build script is `tools/build_openssl.sh`. It checks the SHA-256 of the source archive. A build from the source has the TLS client with the CMake option `-DCHDASH_TLS=ON`.
- ChDash verifies the certificate chain and the name of the host. The host of the URI must be in the subject alternative names of the certificate.
- The URI parameters are `secure`, `verify`, `ca`, `ca_dir` and `sni` (docs/configuration.md, "TLS to ClickHouse"). The port is 9440 when `secure=1` and the URI names none.
- The same parameters apply to `runner_uri`, `system_uri` and `mcp_uri`.

## Checks at start

- A boolean parameter takes `1`, `true`, `yes`, `on`, `0`, `false`, `no` or `off`. Another text stops the start. Before, `secure=ture` was read as `secure=0` and gave a plain connection.
- `verify`, `ca`, `ca_dir` and `sni` need `secure=1`. A URI that sets one of them without TLS stops the start.
- With `secure=1`, the file of `ca` must be a readable file and `ca_dir` must be a directory. A build without TLS stops the start and names the CMake option.
- `verify=0` writes a warning `config.warning` for each URI that has it.

## Not in this release

- ChDash does not send a client certificate. A ClickHouse server that needs one refuses ChDash.
- The link to the PDP and the OTLP export stay on `http`. They have no TLS client.

## Validation

- `tests/tls/run.sh` starts a ClickHouse server with a TLS port and starts the binary once for each case. The cases are: the chain and the name are verified (the host is up), a CA that the system does not know (down), `verify=0` (up, with a warning), a name that is not in the certificate (down), another CA (down), the TLS port with no `secure` (down), the plain port (up), and the four start errors above. The test passes on the binary that the release recipe builds (Zig, musl, static-pie, OpenSSL built with the same compiler).
- `chdash_config_test`: 2541 checks, no failure, with the TLS client built in.
- The release job runs `chdash --print-config` on each binary with a URI that has `secure=1`, so a binary without the TLS client is never published.
