# v1.4.0 — The approval of an action by a person

Base: release 1.3.1. ChDash now follows section 17 of ProcurAuth for each action (ProcurAuth commit `48f3d3a`). The PDP can ask for the approval of a person before a use. An agent that calls an MCP tool then gets a result that tells that the action waits, and the tool runs after the approval. This holds in the identity mode and for each key of the page in the mode `keys` (the creator of the key approves). A page or a route of the API cannot wait, so it refuses. The details are in `docs/access.md` ("Approval of an action"), `docs/mcp.md` and `docs/conformance.md`.

The version of the product comes from the tag. The release workflow reads the tag `v1.4.0` and gives `1.4.0` to the build (`CHDASH_SEMVER_VALUE`). No file of the repository holds the number of the build. The text of the download links (`README.md`, `PRODUCT.md`, `docs/index.html`, `docs/assets/site.js`) holds the number of the last release and changes with each release.

## Breaking changes

- **A route that needs an approval gives `403` with the body `{"error": "approval_cannot_wait"}`.** A page or a route of the API cannot wait for a person (ProcurAuth 17.7a). When the PDP answers `approval_required` to a question of a route, ChDash sends no effect and submits no request. Before, such an answer gave the `403` `forbidden`, and a run of a statement that changes data could fall back to `readonly = 1`. The code is stable. The portal never answers `approval_required` until its operator turns the approvals on, so no existing deployment changes before that.
- **The identity mode has no `isError` member in a result without an error.** In the mode `identity`, a result has `isError` only when it is `true` (MCP binding 5.7). The member is optional, and its default is `false`. The mode `keys` does not change.
- **The identity mode does not publish the actions `mcp.keys.read` and `mcp.keys.write`.** The mode has no key of ChDash to read or to write: the keys live in the portal. The document of the actions does not list them, and the MCP page is not shown. The mode `keys` publishes them as before. A grant on these actions in the portal does nothing in the identity mode.
- **Each tool of the identity mode accepts the control arguments** `approval_ref`, `lease_s`, `until`, `wait_s` and `supersedes`. The schema of each tool in `tools/list` lists them. They never reach the tool and never enter the effect. A call that does not need an approval does not need them.
- **Each key of the page that has a creator (the mode `keys`) accepts the control arguments too.** `tools/list` shows them and gives the tool `get_action_status`. A key of the configuration has no creator: it does not change. A reason `approval_required` for the creator is no more a refusal of the key.
- **`tools/list` of the identity mode names new tools:** `get_action_status` (always), `export_query` (for each host that has `mcp_uri`) and `run_write_query` (for each host that has `mcp_write_uri`).

## What is new

- **The approval for each action.** The PDP decides which grant needs an approval (the property `confirm`). ChDash asks the question of ProcurAuth 10.1 with no effect. A call that needs no approval costs this one question, as before. On `approval_required`, a tool call (`tools/call` of the identity mode) builds the `op` and the `view`. It computes the effect (JCS and SHA-256) and asks again with the effect. Then it submits the request to the approval API of the PDP. The result is not an error: `{"action": {"id", "status": "awaiting_approval", "code", "executed": false}}`, with `NOT EXECUTED` in the second item of `content`. After the approval, the agent calls the tool again with the same arguments. The PDP consumes the approval with the question that has `context.usage`, and the tool runs one time. ChDash keeps no state and never keeps an answer to a question with an effect.
- **The approval for the keys of the page.** The creator of a key is the subject of the PDP, so a key has the same lazy flow, the same `op` and `view`, the same result that waits, `get_action_status` and the same errors. The phone of the creator shows the request. A key of the configuration has no creator and no PDP question, so it stays outside the approval. The action `mcp.keys.write` cannot wait: a person with `confirm` on it gets `403` with `approval_cannot_wait`. The limits of the mode are in `docs/access.md` ("The keys of the page"). `run_write_query` and `export_query` stay in the identity mode.
- **The errors of the approval.** `approval_denied`, `approval_expired`, `approval_unavailable` (retryable), `approval_rate_limited` (retryable, with `retry_after`) and `invalid_argument` (a bad control, no control when an approval is needed, a command above `max_command_bytes`). Another failure of the approval API gives HTTP `503`. The messages are fixed. ChDash never reads or logs an explanation, a comment of a refusal, the approver or the device.
- **`get_action_status`.** The tool reads the verdict of a request (`pending`, `approved`, `denied` or `void`) and renews the lease for the agent. ChDash never renews on a timer, and the call of another tool never renews. `wait_s` makes a call wait for a verdict, up to `access.approval.wait`.
- **`op` and `view` for each tool.** `run_write_query`, `run_query`, `explain_query` and `export_query` show the SQL, the host and the ClickHouse user. Another tool shows its arguments with the defaults of the tool. A view has only JSON Pointers into the `op`. A command above `access.approval.max_command_bytes` is refused, never cut.
- **The write tool `run_write_query`.** It runs one statement that changes data or the schema. It uses the write account of the host (`mcp_write_uri`). It waits for the approval when the PDP asks for one. The statement checks, the guard rails and the annotations are in `docs/mcp.md` ("The write tool"). A host without `mcp_write_uri` has no write tool.
- **The export tool `export_query`.** It runs one read statement and gives its rows as CSV or JSON text, for the action `query.export` (budget `exports`). It also needs `query.run.read` on the host. With it, each action of the document that the identity mode publishes has an MCP tool, so the conformance case U111 passes.
- **The call log.** A call that had an effect has the fields `approval.effect`, `approval.outcome` and, for a write, `approval.executed_sql`. The owner of the portal compares them with the history of the phone to find a substitution. They are the only places where the log holds SQL.
- **The conformance run.** The profile has `approval_calls`, one call for each action. The runner of ProcurAuth (main of 2026-11-10) runs 117 cases. `tests/conformance/run.sh` creates the write account, and the workflow `conformance.yml` checks out the commit `48f3d3abd977f2bd4a49ab856f000c77cf396b4e`. `docs/conformance.md` has the result.
- **New keys.** `access.approval.wait` (`15s`, 0s to 30s), `access.approval.max_command_bytes` (`16384`, 1024 to 1048576), and for each `clickhouse.host`: `mcp_write_uri`, `mcp_write_password_env` and `mcp_write_password_file`. The closed schema, `--print-config` and the reference (`docs/configuration-reference.md`) have them. These contradictions stop the start. `mcp_write_uri` without `mcp_uri`. `mcp_write_uri` with the same user as `mcp_uri`, `runner_uri` or `system_uri`. `mcp_write_uri` without `mcp.auth_mode = "identity"`, or with `access.mode = "open"`. An `access.approval` block with the open mode.

## Upgrade

1. Nothing is required. Without `mcp_write_uri` and without a grant that has `confirm`, ChDash behaves as 1.3.1, apart from the breaking changes above.
2. A client of the identity mode that reads `isError` must treat a missing member as `false`.
3. A grant on `mcp.keys.read` or `mcp.keys.write` of a deployment in the identity mode does nothing. Remove it from the grants.
4. To let an agent write, make a ClickHouse user with only the grants that a statement needs. It must be another user than the MCP user. Set `mcp_write_uri` on the host, with `mcp_write_password_env` or `mcp_write_password_file`. Give `query.run.write` on the host to the key in the portal. Add `confirm` to the grant to ask for the approval of a person. The owner of the key needs a phone, or `web_approval`.
5. The approval API (`/approval/v1/requests`) has no TLS, like the PDP listener. Use a private network, or terminate TLS in front of the PDP.
6. Check that `access.approval.max_command_bytes` is not above `inbox.approvals.max_command_bytes` of the portal.

## Open points

- A person in a browser cannot approve an action of a page: ChDash refuses it (`approval_cannot_wait`), as ProcurAuth 17.7a says.
- The approval of a key belongs to its creator, the action, the node and the effect, not to the key. Two keys of one creator that make the same call share one approval, and the first call consumes it.
- A call of a key whose scope has several databases that need an approval, with a tool that names none, fails closed (the answer of a tool that does not exist). Give the key one database, or put `confirm` on the host.
- The tools that use no action (`list_hosts` and the analysis of the key itself) ask no PDP question in the mode `keys`, so they need no approval there.
- The conformance runner of ProcurAuth has no profile for the mode `keys`, so no case covers it. The native tests and `test_approval_keys.py` cover it.

- **Official suite** (`docker compose --profile test up --build`, one run after the last code change): exit code 0. Backend-functional with the harness: 2378 passed, 148 skipped, 0 failed. - **Fixture of the tests, fixed in this release.** Five tests failed on the earlier runs, and they did not depend on the product code. The cause was in the fixture. The rows of `chdash_ui.weather_observations` had fixed dates of September 2026, and the TTL rule moves a row to the volume `warm` after 60 days. The storage policy `fixture_tiered` also had the default `move_factor` (0.1), so each part moved to `warm` when the host disk had less than 10 % free space. The rows now have dates relative to the day of the start, and the policy has `move_factor` 0 (`tests/clickhouse-config/fixture-storage.xml`). `test_system.py` expects this value.

The runner has no profile for the mode `keys`: the keys of the page are tested by `tests/native/approval_test.cpp` and `tests/backend-functional/test_approval_keys.py`.
