# v45 — Gap-preserving Pipeline activity timeline

## Base

This patch starts from the exact uploaded `Clickhouse-dash(8).zip` snapshot.
The snapshot already contains the v44 correctness/bounded-matching work.

This release keeps these v44 changes:

- UInt64-safe identities
- host/query-scoped graph links
- query-aware trace ownership
- stage-boundary flow accounting
- bounded cost matching
- independent summary/tracing errors
- static asset dependency tracking

## Problem fixed

v44 still grouped every OpenTelemetry call for one processor instance into a
single `(min(start), max(finish))` envelope. A processor ran for 230 ms in
many short bursts, between 5 ms and 6.38 s. As a result, it appeared as one
solid 6.38 s bar.

The label warned that the envelope can contain idle gaps. But the visual still
showed the lifetime as continuous activity.

The Pipeline works on streams: source, expression and aggregation processors can
legitimately overlap or alternate. The UI must keep the measured activity gaps.
It must not show a solid lifetime bar or a fake sequential stage model.

## Implementation

The full-trace summary now adds an adaptive time bucket to its grouping key:

```text
trace_id + parent_span_id + operation_name + time bucket
```

Each returned row still contains the measured minimum start, maximum finish,
active-time sum and event count for that slice. The frontend uses exact-key
aggregation. It joins all slices of the same processor instance. It adds their
active time for stage association.

After stage assignment, combine rows with the same bucket only within that
stage. Keep distinct buckets separate. Do not combine them again into one lifetime
envelope.

The code derives the bucket size from the ClickHouse query-log wall-clock extent and
the number of profiled processors. It targets about 32K summary rows, with 4 to
512 buckets per processor and the existing independent 65,536-row hard cap.
As a result, normal pipelines keep fine temporal resolution. Very large
pipelines stay bounded.

The Pipeline text now calls these bars activity windows. Empty space between
bars means measured idle or non-attributed time at the summary resolution. The
first-to-last envelope no longer fills this space silently.

Bucketed blocks also show average processor utilization through height and
opacity. Sparse, repeated work looks different from continuous work.

## Compatibility

This release needs no database migration.

The summary row schema does not change. One exact
`trace_id + parent_span_id + operation_name` instance can have multiple rows.

The analysis response adds one top-level numeric field: `processor_trace_bucket_us`.
The browser uses this field to read the adaptive temporal resolution. Older
payloads that lack the field use legacy envelope rendering.
