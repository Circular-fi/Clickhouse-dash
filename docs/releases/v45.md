# v45 — Gap-preserving Pipeline activity timeline

## Base

This patch is generated against the exact uploaded `Clickhouse-dash(8).zip`
snapshot, which already contains the v44 correctness/bounded-matching work.
The v44 changes are retained: UInt64-safe identities, host/query-scoped graph
links, query-aware trace ownership, stage-boundary flow accounting, bounded
cost matching, independent summary/tracing errors and static asset dependency
tracking.

## Problem fixed

v44 still grouped every OpenTelemetry call for one processor instance into a
single `(min(start), max(finish))` envelope. A processor that ran for 230 ms in
many short bursts between 5 ms and 6.38 s therefore appeared as one solid 6.38 s
bar. The label warned that the envelope could contain idle gaps, but the visual
still encoded lifetime as continuous activity.

The Pipeline is streaming: source, expression and aggregation processors can
legitimately overlap or alternate. The UI must preserve those measured activity
gaps rather than force either a solid lifetime bar or a fake sequential stage
model.

## Implementation

The full-trace summary now adds an adaptive time bucket to its grouping key:

```text
trace_id + parent_span_id + operation_name + time bucket
```

Each returned row still contains the measured minimum start, maximum finish,
active-time sum and event count for that slice. The frontend exact-key aggregation
reassembles all slices belonging to the same processor instance and sums their
active time for stage association. After stage assignment, rows that share the
same bucket are combined only within that stage; distinct buckets remain distinct
instead of being merged back into one lifetime envelope.

The bucket size is derived from the ClickHouse query-log wall-clock extent and
the number of profiled processors. It targets about 32K summary rows, with 4 to
512 buckets per processor and the existing independent 65,536-row hard cap.
Normal pipelines therefore keep fine temporal resolution while very large
pipelines remain bounded.

The Pipeline text now calls these bars activity windows. Empty space between
bars means measured idle/non-attributed time at the summary resolution; it is no
longer silently filled by the first-to-last envelope. Bucketed blocks also encode
average processor utilization through height and opacity, making sparse recurring work
visually different from continuous work.

## Compatibility

No database migration is required. The summary row schema remains unchanged;
there can simply be multiple rows for one exact
`trace_id + parent_span_id + operation_name` instance. The analysis response adds
one top-level numeric field, `processor_trace_bucket_us`, so the browser can
interpret the adaptive temporal resolution. Older payloads without the field
continue to use legacy envelope rendering.
