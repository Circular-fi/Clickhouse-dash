# v1.3.0 — ChDash is a service of ProcurAuth

Base: release 1.2.2. ChDash is now a conforming service (PEP) of ProcurAuth, the profile of OpenID AuthZEN 1.0 that the portal uses. The access mode `authzen` gets limits, budgets, a route of the resources, TLS to the PDP and an MCP mode with the identity token. The open mode does not change. The details are in `docs/access.md`, `docs/mcp.md` and `docs/conformance.md`.

## Breaking changes

- **The path of the document of the actions.** ChDash serves the document only at `GET /.well-known/procurauth/actions` (ProcurAuth 5.1). The former path `/.well-known/access-actions` has no alias and gives `404`. A system that reads the document, for example the label or the annotation `portal.actions` of the portal, must use the new path in the same deployment.
- **A failure of the PDP gives 503, not 403.** When the PDP gives no valid answer (no answer in `pdp.timeout`, a status that is not `200`, a body that is not valid, a `401` or `403` of the PDP), the route answers `503` with `pdp_unavailable` and `retryable` true. A page gives a page "try again later", not the `403` page. `GET /api/version` also answers `503`.
- **A spent budget gives 429.** A `false` answer with the reason `budget_exceeded` gives `429` with `Retry-After` and the code `too_many_requests`. ChDash never sends `context.reason` to the client.
- **The header `typ` of the identity token must be exactly `JWT`.** A token without `typ`, or with `jwt`, `JOSE` or `at+jwt`, gets `401`.
- **The key is selected by `kid`.** A token with a header `kid` is verified with the configured key of this `kid` only. A `kid` that no configured key has gives `401` (reason `kid`). The `kid` of a PEM key is its RFC 7638 thumbprint, the same value that the portal sends. A token without `kid` is verified with each key, as before.
- **A tolerance on `exp`.** A token is refused only when the time is after `exp` plus `access.identity.clock_skew` (default 60 s). The same tolerance applies to `iat` and `nbf` in the future. Before, `exp` had no tolerance.
- **A token has 16 KiB at most** (before: 8 KiB).
- **The action `system.kill_query` is gone.** No route used it (ProcurAuth 5.2a). A grant on it does nothing.
- **The catalog of the Explorer lists only the databases that the person may read**, for each host that the person can see. A person with `explorer.read` on one database sees that database. Before, such a person got `403` on the catalog.
- **MCP: the 401 and the 429 of `POST /mcp` have an empty body**, in the two modes (MCP binding 5.2, 7.4). `WWW-Authenticate` and `Retry-After` stay. Before, they had a JSON-RPC error.
- **MCP keys mode: a failure of the PDP gives 503.** When the PDP gives no valid answer for the creator of a key, the request gets HTTP `503` with `-32603`, as the routes and the mode `identity`. Before, a call got `-32602`, the answer of a tool that does not exist.
- **MCP keys mode: a key whose creator has a ceiling.** A key cannot apply a ceiling. ChDash refuses to make or adopt such a key (`403` `key_ceiling_unsupported`). A call of a tool of such a key gets HTTP `403` with `-32001` and a fixed message.
- **More than 256 hosts stop the start** in the mode `authzen` (ProcurAuth 5.3c).
- **A PDP URL with `http` to a host that is not the local machine writes a warning** at each start, because the token and the decisions go in clear text. The start does not stop.
- **The start reads the metadata of the PDP** (`/.well-known/authzen-configuration`). A document that names another `policy_decision_point` or another origin stops the start. A PDP without metadata (`404`) keeps the default paths. A PDP that is down at the start gives a warning, and the decisions give `503` until the PDP answers.
- **`server.listen_host = "0.0.0.0"` with `authzen` writes a warning**: only the access gateway must reach ChDash.
- `access.pdp.verify = false` together with `access.pdp.ca_file` stops the start.
- **An `access.pdp.timeout` above `2s` needs `access.pdp.batch_timeout`.** The new key `access.pdp.batch_timeout` (default `2s`) cannot be shorter than `access.pdp.timeout`. A configuration with a longer timeout and no `batch_timeout` stops the start, and the message tells the value to set.
- **A PDP that publishes `procurauth_usage_max_seconds` above `access.pdp.usage_max_seconds` (default `120`) stops the start.** The message gives the value of the metadata and the limit. ChDash never lowers the published time. The portal 5.0.2 does not publish this member.

## What is new

- **Ceilings.** The document declares six ceilings: `max_rows_read`, `max_read_size`, `max_rows`, `max_result_size`, `max_duration` and `max_memory`. The PDP gives their values in `context.limits` of a `true` answer. ChDash applies the lower value of the ceiling, the bound of the configuration and the settings profile of ClickHouse. A run of a person with read and write gets the ceilings of the class of its SQL. ChDash also counts the rows, the bytes and the time of a statement, so a `SETTINGS` clause cannot loosen a ceiling. A `true` answer with a ceiling that ChDash cannot apply is a `false` answer (ProcurAuth 7.5). The statements that ChDash writes for itself (ACL discovery, probes, schema reads of the editor, `query_log`) are internal: no ceiling applies to them. The list of the functions of the Explorer and the reads of the structure of the tables of the signals obey the ceilings of the caller.
- **A result past a ceiling is a refusal.** A route whose statement goes past a row or byte ceiling (`max_rows_read`, `max_read_size`, `max_rows`, `max_result_size`) answers `403` with the code `ceiling_exceeded` and the members `action`, `ceiling` and `limit`. ChDash never sends a cut answer for a ceiling: the preview of a table that a ceiling bounds is refused, not cut. Before, a page answered `422` `<page>_scan_limit`, a `503` of the route, or a cut answer. `max_duration` and `max_memory` keep their answers (`504` and `422`).
- **The screens that a low `max_rows` refuses.** With a low `max_rows` (for example 100), these screens get the refusal `403` `ceiling_exceeded` when a list of the screen has more rows than the ceiling:
  - The Explorer (`explorer.read`): the list of the functions (about 1,500 functions), the catalog when a host has more databases or a database has more objects than the ceiling, the table card when a table has more columns or related objects, the graph and the storage map, and the preview when its `LIMIT` (100 by default) is above the ceiling.
  - Logs, Traces and Metrics (`observability.read`): a page of search results, the facets and the catalog of the metrics. Below the number of the columns of the logs table (about 20), each request of Logs is refused, because the read of the columns obeys the ceiling.
  - The System page (`system.read`): Overview, Queries and Disks, when a list (the databases by size, the running queries, the top queries) has more rows than the ceiling.
  - The editor of the Query page keeps working: the reads of `GET /api/meta` are internal. A run past `max_rows` ends with the `error` event `query_result_limit`, as before.
  - A low `max_rows_read` gives the same refusal on each statement of a page that reads more rows.
- **Shared caches and ceilings.** A request with a ceiling does not use the shared caches of the answers of the Explorer, of the System page and of the data of the observability pages. It runs its own statements, so its ceilings bound them, and ChDash does not keep its answer for the other persons. A request without a ceiling uses the caches as before. `docs/access.md` lists each cache and the reason.
- **Budgets.** The document declares the budgets `queries` (`query.run.read`, `query.run.write`), `exports` (`query.export`) and `requests` (`mcp.session`). Each run, Deep Analyze replay, export stream, MCP call of a tool of `query.run.read` (`run_query`, `explain_query`, `format_sql`, `explorer_names`, `query_execution`) and request of MCP without a tool sends one question with `context.usage` equal to `{"units": 1}`. ChDash never sends this question again after a timeout and never keeps an answer that took a unit. An export takes its unit at the stream, not at `/api/export/run`.
- **The tools of `query.run.read` take a unit in the mode `identity`.** `run_query`, `explain_query`, `format_sql`, `explorer_names` and `query_execution` each take one unit of the budget `queries` of the subject of the token for each call. A call without a host runs nothing and takes no unit. An API tool calls its route in the process, and the route asks the PDP nothing, so a call takes one unit at most. The web routes of the formatter, of the names of the editor and of the record of a run take no unit.
- **The keys of MCP use the budget of their creator.** The mode `identity` and the mode `keys` count the same calls. In the mode `keys`, each call of a tool of `query.run.read` (`run_query`, `explain_query`, `format_sql`, `explorer_names`, `query_execution`) takes one unit of the budget `queries` of the person who made the key. The question goes for the creator, with `context.usage`, on the host of the call. A spent budget gives the tool error `budget_exceeded` with `retry_after`. No valid answer gives HTTP `503`. Thus a key does not let a person run more queries than the budget gives.
- **The route of the resources.** `GET /.well-known/procurauth/resources` lists the hosts, and the databases of a host, that the person may see (ProcurAuth 5.6 to 5.9). The document has the member `resources` with the hosts.
- **TLS to the PDP.** `access.pdp.url` can be `https`. The new keys `access.pdp.ca_file` and `access.pdp.verify` control the check of the certificate.
- **Discovery of the PDP.** ChDash reads the endpoints and the bounds of the PDP from its metadata. It cuts a large batch into chunks within the bounds of the PDP, and a failure of one chunk fails closed.
- **One deadline for a split batch.** All the requests of one batch that ChDash splits have one deadline, `access.pdp.batch_timeout` (`2s`). The last request gets the time that remains. When the deadline cuts the batch, every question of the batch fails and the route answers `503`: ChDash never allows on a part of the answers.
- **A limit on the wait of a use.** ChDash waits for the answer to a question with `context.usage` one second more than `procurauth_usage_max_seconds` of the metadata. The new key `access.pdp.usage_max_seconds` (`120`, 1 to 3600) bounds this published time. A higher value stops the start, and a later document with a higher value is not used. The former code cut the value at 3600 without a message.
- **JWK Set keys.** `access.identity.public_keys` also takes a JWK Set (RFC 7517), for example the output of `portal identity-public-key`.
- **MCP identity mode.** `mcp.auth_mode = "identity"` makes `POST /mcp` take the identity token of the access gateway, also for the subjects `key:<id>` of the portal. The PDP decides each request: `mcp.session`, `tools/list` and the action of each tool. The default `keys` keeps the keys of ChDash.
- **Resource Search (option).** With `access.pdp.search = true`, and only when the metadata announces `search_resource_endpoint`, one AuthZEN Resource Search for each action lists the databases. A failure goes back to the evaluations.
- **The conformance run.** `tests/conformance/run.sh` runs the runner of ProcurAuth (role `pep`) against a binary. `tests/conformance/expected.txt` lists the known failures with their reasons, and it is empty. The workflow `conformance.yml` checks out the fixed ProcurAuth commit `7b1365206a363833ffe104b74357869636a4bb3f`. `docs/conformance.md` tells how to bump it. The profile gives the operation `use_ceiling` (the list of the functions, `max_rows`) the value 1000000: the list does not go past it, so the case U37 tests the acceptance of a ceiling. ProcurAuth decision 69 writes this rule of a profile.
- New keys: `access.identity.clock_skew` (`60s`, 0s to 5m), `access.pdp.ca_file` (the store of the system), `access.pdp.verify` (`true`), `access.pdp.search` (`false`), `mcp.auth_mode` (`keys`), `query.max_bytes_to_read` and `generated_queries.max_bytes_to_read` (`0`, the settings profile decides), `access.pdp.batch_timeout` (`2s`, 10ms to 5m, not less than `access.pdp.timeout`), `access.pdp.usage_max_seconds` (`120`, 1 to 3600). `docs/configuration-reference.md` gives the range of each key.

## Upgrade

1. Change the URL of the document of the actions in the system that reads it, in the same deployment as the binary. For the portal: the annotation or the label `portal.actions` must end with `/.well-known/procurauth/actions`. The portal 5.0.2 already uses this path when the label is absent. Without this change, the portal keeps its last good copy for `access.actions_max_age`. After that time, the PDP of the portal refuses each action below the service, also for the superadmin.
2. The tokens of the portal 5.0 and later have `typ` `JWT` and a `kid` equal to the thumbprint of the key. Keep the PEM key of the portal, or give the JWK Set of `portal identity-public-key`. Do not declare another `kid` for the key of the portal.
3. Read the warnings of the start (`config.warning`). A PDP link in clear text inside a closed network can stay, or move to `https` with `access.pdp.ca_file`.
4. A grant on `system.kill_query` does nothing. Remove it from the grants.
5. The PDP can now give ceilings and budgets. Give them in the portal only after this version is in place.
6. A client of the API must treat `503` with `pdp_unavailable` and `429` with `Retry-After` as "try again".
