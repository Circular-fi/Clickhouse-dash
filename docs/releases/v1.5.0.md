# v1.5.0 — Alignment with ProcurAuth and the portal

Base: release 1.4.0. Three read-only audits compared the ProcurAuth specification, the portal and ChDash. This release fixes the points on the side of ChDash. The rule of the owner is that each function of a service must be able to wait for an approval. The document of the actions must also be true. So ChDash publishes an action only when a tool serves it, and it adds the missing tool for the query library. The details are in `docs/access.md` ("Actions and tools", "Routes with no action"), `docs/mcp.md` and `docs/conformance.md`.

The version of the product comes from the tag. The release workflow reads the tag `v1.5.0` and gives `1.5.0` to the build (`CHDASH_SEMVER_VALUE`). No file of the repository holds the number of the build. The text of the download links (`README.md`, `PRODUCT.md`, `docs/index.html`, `docs/assets/site.js`) holds the number of the last release and changes with each release.

## The one exception to the rule

A page or a route of the API cannot wait for an approval. ChDash keeps the answer `403` with the body `{"error": "approval_cannot_wait"}` for them. This is the one exception to the rule that each function can wait. The reason is ProcurAuth 17.7a. An HTTP request of a browser cannot receive the result "the action waits". It cannot carry the control arguments of the agent. It cannot be sent again with the same effect. The specification has no form of a page that waits. A grant with `confirm` on an action makes the pages of this action unusable for the person. The MCP tool of the same action can wait. Give `confirm` only to the grants of agents and of keys.

Two more cases stay outside the approval, because they have no subject for the PDP to decide: the keys of the configuration, and the mode `open` of the access (and the probes). `docs/access.md` says so ("Routes with no action").

## Breaking changes

- **An action that no tool serves is not published.** While MCP is on, the document of the actions lists an action only when a tool serves it. A grant of the portal for an action that is not published does nothing. A person cannot use the action: ChDash answers `403` without a question to the PDP. The Query page runs each statement with `readonly = 1`. These actions change:
  - `query.run.write` is published only when `mcp.auth_mode` is `identity` and a host has `mcp_write_uri` (the tool `run_write_query`).
  - `query.export` is published only when `mcp.auth_mode` is `identity` and a host has `mcp_uri` (the tool `export_query`).
  - `library.write` is published only when a library is writable and `mcp.auth_mode` is `identity` (the new tool `library_write`).
  - `mcp.usage.read` is published only when `mcp.usage.enabled` is `true` (and, in the identity mode, `mcp.usage.all_keys`).
  - **The mode `keys` loses `query.run.write`, `query.export` and `library.write`.** This is a breaking change for a deployment with MCP on in the mode `keys` under `access.mode = "authzen"`. The reason: the mode `keys` has no tool that serves these actions, so no use of them can wait for an approval, and a service must not publish an action that cannot be approved. After the upgrade, the Query page of such a deployment runs each statement with `readonly = 1`, and the export routes answer `403`. The way out is the identity mode (`mcp.auth_mode = "identity"` with `mcp_write_uri`, `mcp_uri` and a writable library, which have the three tools), or MCP off. The mode `keys` still publishes `mcp.keys.read`, `mcp.keys.write` and `mcp.usage.read` for its pages. These actions have no tool, and a page cannot wait.
  - With MCP off, nothing changes: no tool exists, and the pages publish what they serve.
- **A link to the PDP that is not secure stops the start.** A `http` URL to a host that is not this machine stops the start. So does `pdp.verify = false`. Before, they gave a warning. The new key `access.pdp.insecure_link` (default `false`) accepts them, with a warning. The key stops the start when the link is secure (the two lines contradict each other).
- **The `op` of an approval has more members.** It has the caps of the call: `max_rows`, `max_result_bytes` and `timeout_seconds` (ProcurAuth 17.3a). An approval that the PDP gave before the upgrade does not match the new effect: the agent asks again.
- **A bound of the command and of the view.** `access.approval.max_command_bytes` and `procurauth_approval_max_command_bytes` of the PDP bound the size of `op` and `view`. The lower value applies. A part of the view above its limit (title 128 characters, field value 256 characters, body 16 KiB) gives the tool error `invalid_argument` (contract 9.5). A statement above 16 KiB cannot be approved. A `lease_s` outside the bounds of the PDP gives the same error.
- **The faults of the approval API are tool errors.** `explanation_required` and `cannot_supersede` give `invalid_argument`. A late `invalid_evaluation` makes ChDash ask again. A second refusal gives `approval_expired`. Before, they gave HTTP `503`. The alias `no_phone` is removed (use `no_device`).
- **The tools `list_hosts`, `mcp_analysis_my_limits` and `mcp_analysis_my_usage` no longer use `mcp.session`.** A tool never uses `mcp.session`: a grant with `confirm` on it would refuse the whole endpoint. `list_hosts` has the new action `mcp.hosts.read`. The two analysis tools have the new action `mcp.analysis.read`. Both are published in the identity mode only, and they list no budget. `mcp.session` stays for the requests that call no tool (`initialize`, `ping`, `server/discover`, the notifications). The portal must grant the two new actions to the people and the keys that use these tools. The mode `keys` has no action for these tools.
- **The approval of `export_query` follows the action of the use alone** (spec question 53). Only `confirm` on `query.export` submits the call for approval. A reason of ProcurAuth 17.1 for `query.run.read` (the scope) gives the tool error `scope_needs_approval`, and nothing goes to the approval API.
- **The state of a key of the page is a question for the display** (ProcurAuth 4.4 and 10.1). The batch has the match `subtree`. A key whose creator has a grant with a ceiling keeps the tool in `tools/list`; the call gets the refusal of a key that cannot apply a ceiling (`403`, `-32001`). Before, the tool left the list.
- **A key of the page that reaches several databases gets a tool error.** Several databases can need an approval while the call names none. The error is then `invalid_argument`, with a message that tells what to change. Before, the agent got the answer of a tool that does not exist.
- **Requests with no valid key are limited for each client address** (contract 3.9): `mcp.unauthenticated_rate_limit_per_minute`, default `10`. The next request gets `429` with `Retry-After` and no body. `0` removes the limit. Behind a reverse proxy, the address is the address of the proxy.
- **`tools/list` of the identity mode and of the keys with a creator** adds the four facts of contract 4.4 to the description of each tool. It also adds an `outputSchema` (contract 4.5) to each tool. It names `get_action_status` only when it names at least one other tool.
- **The catalog, the storage map and the graph of the Explorer follow ProcurAuth 4.4 strictly.** The route asks `node` on the host first. A person who has only a decision on some databases (the match `subtree` on the host) still sees the host, but ChDash reads only the databases that a `node` decision allows. It lists the names of the databases as candidates (never shown), asks `node` for each one, and builds the catalog, the storage map and the graph from the allowed databases only. Nothing of this read is kept or shared with another person. The route answers `403` when no database is allowed. A filtered read costs more than a cached read.
- **The stream and the cancel of a run belong to the subject that started it.** Another subject gets the answer for an unknown `query_id`.
- **`export_query` follows the order of contract 9.4.** The check of the arguments comes before any question to the PDP. The ceilings of `query.run.read` apply to the export. The lowest value of each ceiling wins.
- **A ceiling `max_memory` is refused when the profile of the MCP user has `readonly = 1`.** ClickHouse takes no setting then. ChDash cannot count the memory of a statement. The call gets the tool error `ceiling_unenforceable`. The ceilings `max_rows_read`, `max_read_size` and `max_duration` are now counted by ChDash in this case, as they are on the pages.
- **The evaluation_id may have 4096 bytes** (1024 before). A longer one is not kept: the answer is a denial that cannot start an approval, never an outage.

## What is new

- **The tool `library_write`** (identity mode). It changes the query library through the route of the Query page, with the action `library.write`. It has the operations `folder_create`, `folder_update`, `folder_delete`, `query_create`, `query_update`, `query_delete` and `import`.
- **The metadata of the PDP.** ChDash reads `procurauth_approval_max_command_bytes`, `procurauth_approval_lease_min_seconds`, `procurauth_approval_lease_max_seconds` and `procurauth_approval_wait_max_seconds` when the PDP publishes them. It never needs them. The schema of each tool shows the bounds of `lease_s` and `wait_s`.
- **The document and the tools agree.** A native test (`test_actions_and_tools_agree`) checks 216 configurations of the identity mode and the mode `keys`: each published action has a tool, and each tool names a published action or `mcp.session`. The conformance run has three variants: `default`, `full` (a writable library, the traces on) and `lean` (no write account, no usage). The profile has `mcp_call_multi`, so the cases U96 and U97 run.
- **New keys.** `access.pdp.insecure_link` (`false`) and `mcp.unauthenticated_rate_limit_per_minute` (`10`, 0 to 1000000). The closed schema, `--print-config` and the reference (`docs/configuration-reference.md`) have them.
- **Documents.** The probes, `/metrics` and `/api/health` need no token (contract 8.1). `docs/access.md` ("Routes with no action") says what a router must not publish. The stale lines of `docs/mcp.md` and `docs/conformance.md` about the tools with an effect are fixed.

## Upgrade

1. A configuration with `access.pdp.url` as `http` to a host that is not this machine, or with `verify = false`, stops at start. Use `https`, or set `access.pdp.insecure_link = true` on a network that only ChDash and the PDP reach.
2. A deployment with MCP on and `mcp.auth_mode = "keys"` loses the actions `query.run.write`, `query.export` and `library.write` in the document. The Query page then runs each statement with `readonly = 1`, and the export routes answer `403`. To keep them, use the identity mode (with `mcp_write_uri`, `mcp_uri` and a writable library), or turn MCP off.
3. A client that depends on the exact `op` of an approval must add the caps (`max_rows`, `max_result_bytes`, `timeout_seconds`). A client that reads the schema of a tool must accept the new `outputSchema`.
4. A monitoring that scrapes `/metrics` or calls the probes keeps working. Make sure that the router does not publish them (`docs/access.md`, "Routes with no action"). The Home router (`PathPrefix(/clickhouse/)`) publishes them today: exclude `/clickhouse/metrics`, the probes and `/clickhouse/api/health`, or set `server.metrics = false`.
5. A script that sends many requests with a wrong key from one address gets `429` after 10 requests in one minute. Set `mcp.unauthenticated_rate_limit_per_minute = 0` to remove the limit.
6. With the portal, grant `mcp.hosts.read` and `mcp.analysis.read` to the people and the keys that use `list_hosts` and the analysis tools. Give the actions of the table above only when a tool serves them. A grant on `query.run.write` or on `library.write` has no effect when the document does not publish the action.

## Open points

- **Decision of the owner (the keys of the configuration).** A key of the configuration has no PDP question. So it cannot need an approval. The mode `open` is in the same case. ProcurAuth 15 item 7 accepts the exception for the pages, but not for these two cases. The audit asks for a decision: refuse them, or state the exception in the specification.
- **Decision of the owner (the pages).** A page cannot wait. The specification has no form for it. ChDash keeps the `403`.
- **Not in the `op`.** A route of an API tool can set defaults itself, for example a window of time or a page size. These defaults are not in the `op`. The agent must give them as arguments.
- **MCP off.** With MCP off, no tool exists, so the document publishes the actions of the pages. The pages cannot wait.
- **The cancel of Deep Analyze** has the cancel token only: it has no binding to the subject.
