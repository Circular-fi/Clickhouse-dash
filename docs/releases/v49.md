# v49 — Compact processors and bounded Pipeline rendering

Base: the exact `Clickhouse-dash-v48-full.zip` source archive. Processor collection, activity resolution and Pipeline timing semantics do not change.

## Behavior

Processor data now uses the same transport principles as compact spans: one shared string dictionary, positional rows and relative timestamps. The new `processors_compact` block retains every processor field, graph identity, counter and recorded summary window. Unlike the trace display LOD, this encoding does not merge or discard processor activity windows. The encoding transports UInt64 values beyond JavaScript's exact integer range as decimal strings.

Normal analysis responses omit the expanded processor arrays. Debug exports retain them alongside the compact data for diagnosis. The frontend can still read older object-based exports. It reports unsupported or malformed compact formats explicitly.

The browser iterates summary windows. It does not keep a second expanded summary array. The browser caches decoded data and the Pipeline model across tab switches.

Above 150 stages, the browser mounts and draws only visible rows plus overscan. All stages stay available. The user can scroll and sort them. The dialog releases its data, DOM and observers when it closes. Older in-flight responses cannot replace a newer query or repopulate a closed dialog.

## Measured payload size

The measurements in this section cover only the processor and processor-summary blocks. They use minified JSON and gzip. They are not whole-response or Debug ZIP sizes. Compact sizes include the schemas and string dictionary.

| Supplied export | Expanded JSON (bytes) | Compact JSON (bytes) | JSON reduction | Expanded gzip (bytes) | Compact gzip (bytes) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `query (6)(1).zip` | 68,065 | 13,609 | 80.01% | 3,079 | 2,989 |
| `query (7).zip` | 347,623 | 36,890 | 89.39% | 17,294 | 13,613 |

The smaller legacy export already compresses well with gzip. The newer bucketed export also saves 21.29% after gzip. Debug exports include expanded originals on purpose. These reductions therefore describe the normal API processor block.

## Validation

- 418 Python harness checks passed. The run skipped one existing check.
- 27 Pipeline model tests and 8 compact-codec tests passed. The latter used the actual C++ encoder. The test data contained 10,000 processors, 65,536 windows, exact UInt64 values, Unicode/NUL strings, graph scopes and activity gaps.
- Both supplied exports round-trip through the C++ encoder. The encoder keeps every processor and summary field. Their semantic Pipeline models match the expanded-payload models.
- The optional `chdash_processor_codec_test` CMake target configured and compiled successfully. The modified API translation unit also passed a C++ syntax compilation against the project's pinned dependencies.
- Chromium replay covered compact-only API responses, legacy data, zoom/pan/focus/sorting, dark/light themes and 1440/1024/390-pixel viewports. A 10,000-stage fixture mounted 26 rows in the tested desktop viewport. The test also scrolled to the final stage, sorted the rows and resized the view. These functions remained functional.
- Dialog checks covered cached tab switches, close/reopen, stale responses
  and malformed compact payloads. No browser exceptions were observed.
- The incremental patch was applied to a fresh v48 snapshot. Its resulting source matched the release archive. The harness was run again there.

The validation used no live ClickHouse server and no full application rebuild. Collection SQL is unchanged. The tests exercised the actual C++ serializer and browser integration with recorded exports.

## Apply

From the v48 repository root that has `src/` and `tests/`:

```bash
git apply --check /path/to/Clickhouse-dash-v48-to-v49.patch
git apply /path/to/Clickhouse-dash-v48-to-v49.patch
```

Rebuild or restart the application. The backend and the embedded frontend then update together. You do not need a database migration. If the checkout is older than v48, use the full archive or update to v48 first. Then apply this incremental patch.
