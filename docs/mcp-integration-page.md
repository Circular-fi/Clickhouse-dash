# MCP integration page

The **MCP integration** page shows the access keys of ChDash's MCP server and how to connect a client. An AI client (Claude Desktop, Claude Code, an IDE, your own agent) reads your ClickHouse data and the pages of ChDash through the MCP endpoint. Each key limits the host, the tools and the data that its client can use. This file describes the two pages of the section: **Keys** (the access keys and how to connect a client) and **Usage** (what all the keys did: see "The Usage tab"). The server side (the endpoint, the key store, the tools, the `mcp` configuration block) is in `docs/mcp.md`. The usage is counted only when `mcp.usage.enabled` is true: while it is off, the pages say so and keep the rest (see "Usage is off"). Several ChDash may share the directory of the usage: the figures are then the sum of all of them (see "Instances").

## Open the page

The page is at `/mcp-integration`. It is a page of its own (`mcp.html`), like System. It is not tied to a host, so the host picker is hidden.

A row of two links stands under the header, on both pages: **Keys** (`/mcp-integration`) and **Usage** (`/mcp-integration/usage`, `mcpusage.html`). It is the nav row of System: the tab of the current page is underlined and has `aria-current="page"`. The row is in the shell of each page (a script puts the base path of a reverse proxy in its links). It stays when MCP is off: both pages then show "Turn MCP on".

## Layout

The page has the same frame as System and Observability (the header, the nav row of the two links, then one scrolling panel). It has no bar, no strip and no visible title. The page switcher in the header names the page. The `h1` ("MCP integration") is for screen readers only (`srOnly`). The panel is the only scroller. Its inset is `--gutter` (12 px, 10 px at 820 px and below).

```
Keys  Usage                                  the nav row
+-------------------------------------------------+------------------------------+
| Access keys  11    [filter]      (refresh) [+ New key] | Connect a client             |
| Name  Secret     Host Tools Data Limits Used         | Endpoint [ https://host/mcp ]|
| name  a1b2c3d4-..  one line for each key        [x] | [Code|Desktop|Inspector|JSON] |
| Used: ... (a note)    > Deleted keys 2               |                              |
| ...                                                   | command / JSON               |
|                                                       |------------------------------|
|                                                       | Hosts                        |
|                                                       | Global limits                |
+-------------------------------------------------+------------------------------+
```

1. **The keys.** The part "Access keys": its heading (title, count, a filter from 10 keys, then **Refresh** and the primary **New key** at the right end), a note, an alert, then the keys table. It takes the left of the page.
2. **The side column.** One bordered box of three blocks, 36% of the window wide (28 to 42 rem), beside the keys from 1366 px. It stays in view while the keys scroll. The panel keeps the room of its scrollbar (`scrollbar-gutter: stable`) whether the content scrolls or not, so opening the details of a key moves nothing sideways. A key is narrow (a name of 32 characters, the start of its secret), so the column takes the room: the commands and the JSON of the clients read on a few lines.
   - **Connect a client.** The **Endpoint** (a read-only field with its copy button), then the tabs of the clients and one code block. Always open. See below.
   - **Hosts.** The hosts that have an `mcp_uri`: the name, the label (when it is not the name), the ClickHouse user that the tools of a key of this host run as (`chdash_mcp`) and a health badge (`healthy`, `down` or `unknown`). A host whose MCP user cannot connect shows a red **MCP user down** badge instead (its tooltip says why): no key can read it.
   - **Global limits.** A list of the global limits: label at the left, value at the right. The request limit is counted for each key on each instance (every ChDash that shares the usage directory has its own counter), and the note under the list says so.

   Under 1366 px the side column goes under the keys and its three blocks stand side by side (from 760 px). On a phone they stack.

The page says nothing of the state of MCP ("MCP enabled", "Storage configured" or "Managed from the UI" told the reader nothing that he could act on). A page that shows keys has MCP on. What stops a change (no storage file, `manage_from_ui = false`) is the note under the title of the keys.

The page uses the shared components only. `badge` draws the badges. `uiState` draws the loading, empty and error states and the notes. `dialog` draws the dialogs. The form kit (`.uiForm`, `.uiField`, `.uiInput`, `.uiCheck`) draws the fields. The part heading, the compact data table and its box are shared too. `mcp.css` keeps only what this page alone needs.

The page switcher shows an **MCP** entry only when `/api/version` reports `features.mcp.enabled = true`. The switcher caches the answer in `chdash.pageNav.v1`, like the other entries.

ChDash has no login. Anyone who can open the page can create a key and show any secret. A key cannot read more than the ClickHouse MCP user can read (the API tools are the exception: see `docs/mcp.md`). To restrict the page, use your reverse proxy or your network. You can also set `manage_from_ui = false`: the page is then read-only.

## States of the page

| State | What the page shows |
| --- | --- |
| Loading | A spinner and a sentence in `#mcpState` for the first load. A spinner and a sentence for the keys. |
| Error | A message and **Retry**, in `#mcpState` and for the keys. |
| MCP off (`{"enabled": false}` from `/api/mcp/meta`) | The part "Turn MCP on", with the badge "MCP is off", the HCL block and a note. No keys, no side column. |
| Usage off (`usage.enabled` is false in `/api/mcp/meta`) | Usage tab: the state "Usage is off" and no bar (see "Usage is off"); nothing reads the usage. Keys: no column Used, no line of keys that keep usage and no usage in the details of a key; the ClickHouse cost of a key stays. |
| Storage not configured | **New key** is off. The reason shows in the note under the title of the keys. The keys of the config file still show. |
| `manage_from_ui = false` | A read-only note. **New key** and **Delete** are off. |
| No keys | An empty state with **New key** (when the page can create keys). The side column stays, so the commands to connect are next to it. |

A server that does not have the `/api/mcp/*` routes answers `404` for `/api/mcp/meta`. The page treats this as MCP off. The Usage page has its own states (loading, an error with **Try again**, no request): see "The Usage tab".

## Connect a client

One tab for each client, and one block at a time. The blocks use the real endpoint URL and the placeholder `<secret>`. The secret dialog shows the same tabs with the real secret. A line under the block names the protocol versions and says to serve ChDash over HTTPS when a client runs on another machine.

The blocks are **coloured**, with the classes of the SQL highlighter (`.tok-*`), so they follow the colours of the Query editor in both themes: the program, the flags, the URL and the quoted header of a command; the keys, strings and literals of JSON; the labels of the Inspector values; the attributes and blocks of the HCL extract of the MCP-off state. The page cuts the text into text nodes and `<span>` elements (no markup from a value). The copy button copies the plain text.

The header that carries the key is `mcp.auth_header` (`Authorization` by default; `docs/mcp.md`). `/api/mcp/meta` sends it as `auth_header`, and every block uses it. `Authorization` takes `Bearer <secret>`. Another header (for example `X-ChDash-Key`, when a proxy in front of ChDash already uses `Authorization`) takes the secret alone. The line under the blocks names the header.

- **Claude Code.** The `claude mcp add --transport http` command.
- **Desktop** (Claude Desktop). A block for `claude_desktop_config.json`. It starts the `mcp-remote` bridge with `npx`, and the bridge sends the Bearer header. It needs Node.js.
- **Inspector** (MCP Inspector). The `npx @modelcontextprotocol/inspector` command and the values to enter: the transport (Streamable HTTP), the URL and the header.
- **JSON.** The `mcpServers` block of a client that reads a JSON file of servers (`.mcp.json`).

## Keys table

The running text of the page (the notes, the tips of the tools) is justified when it takes several lines.

Each key is one line of the table. The rows keep the order of the API (keys of the config file first). The table uses fixed columns: the name column is narrow (a name has 32 characters at most), the secret shows its start only, so that the column Used fits beside the others, and a cell that is too long ends in an ellipsis. The tooltip of the cell says all of it.

| Column | Content |
| --- | --- |
| Name | The name, a button that opens the details of the key (so does a click on the row outside its buttons). The tooltip also says where the key comes from. |
| Secret | The **first 8 characters** of the secret (its hint, which tells the keys apart), the next group of dots and an ellipsis: `3f2a9c1e-••••…`. The tooltip has the whole mask: the hint, **the hyphens in clear**, and a **dot** for every other character (`3f2a9c1e-••••-••••-••••-••••••••••••`, the `secret_mask` that the server sends), then why the secret cannot be shown. The cell has no button: ChDash keeps only a hash of the secret. A key of a file that kept no hint shows dots only. |
| Host | The name of the host, in the code font, cut with an ellipsis. `None` when the key has no host. A key reads one host. In the warning color: a key of an older file that names several hosts ("2 hosts"), a host that has no `mcp_uri` any more, or a host whose MCP user cannot connect; the tooltip says which. |
| Tools | `n/total` (out of the tools of the server), `All` or `None`. The tooltip lists them. |
| Data | How many databases and tables the key reaches: `3 dbs · 142 tables`. It is what the MCP user of the key's host may read (`CHECK GRANT`), cut by the patterns of the key. The table is drawn first (the cell shows an ellipsis), then one request (`GET /api/mcp/access`) counts every key at once, whatever their number: the grants of a host are read once. In the warning colour when the key reaches nothing (`0 dbs · 0 tables`: the patterns match nothing that the user reads); a dash when the host cannot be counted (the MCP user cannot connect, or the request failed). The tooltip says what the number is (and how many tables are read in part) and lists the patterns. Refresh counts again. |
| Limits | The rows and the timeout, as "100 · 5 s". A value that the key sets shows at full strength. A key without its own value shows the global limit in the muted color. A screen reader reads "(default)" after it. |
| Used | When the key was last used and its tool calls in the last 7 days: `2 h ago · 1.2K` (`format.ago` in its short form, and the compact count). The table is drawn first (the cell shows an ellipsis), then one request (`GET /api/mcp/usage?window=7d`) reads the use of every key. **Never** when the key was never used and the counting covers its life (the key is as young as the counting, `usage.since`, or it comes from the config file, which has no date of creation); a dash when the key is older than the counting (it may have been used before it began). Muted without a call in the window, in the warning colour when 5% of the calls failed or the rate limit refused a request. The tooltip has the time of the last use, the calls among the requests, the errors and the refusals. A note under the table says what the column counts, since when ("Counted since ..." when the window starts before the counting) and, when several instances share the usage, over how many it is summed ("Summed over 3 instances"); a warning follows it when a file of another instance is left out (see "Instances"). Refresh reads it again. **The column is not there while the usage is off.** |
| Actions | **Delete**, a trash icon with no frame around it (like the gear icons), with a label for screen readers and a tooltip. A key that the page cannot delete (a key of the config file, or `manage_from_ui = false`) has nothing in this cell: no icon, no lock. The tooltip of the name says where the key comes from. |

A key has no description, no expiry and no state. Its use shows in the column **Used** and in the usage of its details. A key is **made or deleted**: there is no edit, no disable and no rotation. To change a key, delete it and make a new one.

From 10 keys, the head of the part shows a filter. It matches the name and the source. The count shows "n of N" while the filter is on. The filter text stays after an action.

The table is a compact data table (`.dataTable--compact`) in a hairline box (`.dataTableWrap`). Under 54 rem the box scrolls sideways. From 820 px down, Tools, Data, Limits and Used leave the table (the details of a key show them). On a phone (600 px and below), each key is a card. The name is the first line, then the secret. The hosts, the tools, the data, the limits and the use follow in two columns. **Delete** closes the card, 40 px high. The label of each cell shows above its value. The table keeps its roles for a screen reader.

### The secret of a key

- The secret shows **once**: in the dialog after the create (see "The secret dialog"). The server keeps the SHA-256 of the secret and its first 8 characters. No route gives the secret again, and the table has no eye and no copy button.
- The tooltip of the secret cell says it: a lost secret cannot be found, so delete the key and make a new one.
- The page keeps the secret nowhere: not in `localStorage`, not in `sessionStorage`, not in the address.
- ChDash has no login: anyone who can open the page can make and delete keys. See `docs/mcp.md`, "Security limits".

## Make a key

**New key** opens a dialog. It follows the page that makes a fine-grained token on GitHub (a name, the access, the permissions) and it is dense on purpose. The dialog has **a fixed size** (58 rem wide, 46 rem high, less on a small screen) that does not follow its content: opening a family or showing an error does not resize it. Each column scrolls inside the dialog when it needs to (the permissions column, when families are open). On a screen under 820 px wide, there is one column and the dialog body scrolls. At the left, the name, the host, the data and the limits. At the right, the permissions. The fields that must be filled have a `*`.

- **Name.** 32 characters at most (`a-z`, `0-9`, `-`, `_`). The pattern comes from `/api/mcp/meta` (`name_pattern`).
- **Host.** A key reads one host: one **radio button** for each host that has an `mcp_uri`, **one under the other**. The first host whose MCP user connects is chosen. A host whose MCP user cannot connect is greyed, with the reason ("The MCP user chdash_mcp cannot connect"; the tooltip has the error of ClickHouse). Under the list, a line says which user the tools run as and how many tools it cannot serve. There is no "All hosts" choice: one key for each host.
- **Data.** The patterns, one for each line. A pattern is `db`, `db.table`, or uses `*` as a wildcard. `*` alone is all the data, and it is **the default**: the grants of the MCP user already limit what a key reads, and a pattern narrows it more. There is no "All data" choice: the field holds `*`.
- **Permissions.** One **card for each family** of tools, set apart by a border and a head. The families come from `/api/mcp/meta` (`tool_groups`): the page names none of them, so a family that is added on the server shows without a change here. Today: Data, Explorer, System, Observability, Query, SQL and MCP analysis. A family has at least two tools, so no card is a lone check box (but the analysis family is the one tool that every key has while the usage is off: see "The analysis tools"). Observability has **sections** (Traces, Logs, Metrics: `tool_groups[].sections` and `tools[].section` of `/api/mcp/meta`), drawn as sub-headings of its card, each with its count; the pages' tools and the simple tools of a signal stand together. A card has the check box of the family (all its tools; half ticked when only some are on), what the family is for, how many tools are on ("3/7") and an arrow that opens the tools: one check box each, with what the tool does. **Every permission is read-only, so each one is a check box**: there is no level to choose.
- **The analysis tools.** The family **MCP analysis** (`mcp_analysis`) holds the tools by which a key reads its own limits and usage, and the usage of all the keys. The catalog of the meta says how each one is given (`tools[].always`, `explicit_only` and `available`), and the page names none of them:
  - a tool that **every key has** (`always`: `mcp_analysis_my_limits`, and `mcp_analysis_my_usage` while the usage is on) shows **checked and locked**, with "Every key has it". It is not a choice, and the form never sends it: it sends the names of the boxes that are on and free;
  - a tool that **"*" does not give** (`explicit_only`: `mcp_analysis_all_usage`, which lets a key read the names, hosts, clients and activity of all the keys of all the instances) is a check box of its own. It is off by default, the box of the family and any "all" action leave it alone, and it says `"*" does not include it`. A key has it only when its list names it. The tool exists only while the usage is on and `mcp.usage.all_keys` is true;
  - a tool that is **not available** (`available` is false: the usage is off, or the setting that the tool needs) is not offered. The same holds for any tool of any family.
  The family has no box of its own when it has no plain tool to choose: its head is a title, and its card is **open** (a family that holds a tool to name, or only tools that every key has, shows them at once). With the usage off and `all_keys` off, the family is the one tool `mcp_analysis_my_limits`, checked and locked.
- **Locked tools.** Only the SQL tools need `*`: they are off and locked, with "needs data *" in the head of the family, until the data is `*` alone. If you change the patterns again, the form clears the SQL tools again. All the others need no `*`: the Explorer tools of one table and the catalog are cut by the patterns on top of the grants of the MCP user, and the rest of the Explorer, System, Observability (Traces, Logs, Metrics, with the simple tools too) and Query are read as the pages read them, with the system user (the permission alone gives them).
- **Tools that the host cannot serve.** The tools that need a grant that their user lacks on the chosen host (`system.documentation` for the MCP user; `system.parts` and the `otel` tables for the system user, for every tool of Observability) are off and locked too, with "no grant" in the head of a family that has no other tool. The tooltip of a tool names the grant that is missing and the statement that gives it. When you choose another host, the form locks and clears the tools again for that host. The server refuses such a tool anyway (`not_grantable`, `docs/mcp.md`).
- **Defaults.** The Data family starts on. The others start off, and so does a tool that "*" does not give. The tools that every key has are on and locked.
- **Max rows** and **Timeout.** Optional. An empty field keeps the global limit.

**Create key** is off until the key is valid. Its title says the first thing that is missing ("Enter a name.", "Choose the host that the key reads.", ...). So you cannot send a key with no name or no host. There is no summary line and no description.

An error of the server shows under its field (`error = "validation"`, with `field` and `reason`; `409 name_taken` under the name). The dialog stays open. An answer that names no field shows at the foot of the dialog.

## The details of a key

A click on a key (its name, or its row outside the buttons) opens its details **in a row under the key**, in the table. There is no popup. **One key at a time**: another key closes the first. A second click on the same key closes it. The name is a button with `aria-expanded` and `aria-controls`, and the focus stays on it. The open key stays open when the list is drawn again (Refresh, an action). Deleting a key takes its details with it. The row spans the whole table. It shows:

- the source (this page, or the config file);
- the host (a chip in the code font, and `as chdash_mcp`: the user that its tools run as) and the data (chips; `*` is "all the data"). A key of an older file that names several hosts, a host that is gone and a host whose MCP user cannot connect say so in the warning color;
- the rows and the timeout, with "(default)" when the key sets none;
- **Permissions**, "n of m": every family of the server, in **two balanced columns**: the tallest families go first, each in the shorter column, so both columns end at about the same height; each column keeps the order of the families and has no empty row between two families; on a phone there is one column. Each family has what the key holds in it ("2 of 8") and, under it, the tools it holds with what each one does. A family with no tool is dimmed. A key with `tools = ["*"]` holds every tool it can hold: the tools that need all the data only with the data `*` alone, and not the tools that "*" does not give (`mcp_analysis_all_usage`: a key holds it only when its list names it, as `tools = ["*", "mcp_analysis_all_usage"]`). Every key holds the tools that every key has (`mcp_analysis_my_limits` and `mcp_analysis_my_usage`: "every key has it" stands where a note says what the tool does). The counts ("2 of 26", `5/26` in the table) are out of the tools that the server offers now. A tool that the key holds and that the MCP user of its host cannot serve is struck out, with "not served: chdash_mcp lacks otel.otel_logs" (the tooltip has the `GRANT` statement), and the heading says "3 not served".

Under the permissions, **Data it reads** answers the question "which databases and tables can this key reach?". For the host of the key, the page shows the MCP ClickHouse user (`as chdash_mcp`), the number of tables and databases, and a line that says why: the tables that the user reads (`CHECK GRANT`), and what the patterns of the key keep or leave out. Each database opens on its tables, and a table that the user reads only in part says "some columns". A host that cannot be checked says why. **Check again** asks the grants again (the answer is kept for `explorer.acl_cache_ttl_ms`, 60 s by default). The data comes from `GET /api/mcp/keys/<id>/access` (`docs/mcp.md`). What the key reaches is the grants of the MCP user cut by the key: the key never reads more than the user.

Under it, **Usage** says what the key did (`docs/mcp.md`, "Usage of a key"), read when the details open (`GET /api/mcp/keys/<id>/usage`). **It is not there while the usage is off**:

- a **window**: the buttons `1 h`, `6 h`, `24 h`, `7 d`, `30 d`, `90 d` (and `365 d`), as far as `mcp.usage.retention_days` keeps them (the first three always), `7 d` first. The window that the reader picks stays for the visit of the page, so two keys are compared on the same window. The heading says the dates of the window, then, when several instances share the usage, **Summed over 3 instances** (a button that opens the list of the instances: see "Instances"), and **Open in Usage** (a link) leads to the Usage tab, cut by this key, in the same window (`/mcp-integration/usage?key=<id>&window=<window>`);
- a warning above the tiles when the file of an instance is left out of the sum, or when another ChDash writes under the name of this instance (see "Instances");
- six tiles: the tool calls (and the requests), the errors (and their share: in the warning colour, in the danger colour from 5%), the refused requests (and how many by the rate limit), the time of a call (average and longest), the bytes returned (and the rows of the tools that build their SQL), the last use (and the first);
- the calls of each step of the window, with the errors in the danger colour (the shared sparkline), and the busiest step. The step is the server's (`series.step`, in seconds): a minute for `1 h`, 5 minutes for `6 h`, 15 minutes for `24 h`, 3 hours for `7 d`, 12 hours for `30 d`, a day for `90 d` and `365 d`. The sparkline says it ("Tool calls by 3 hours in the last 7 days"), and the busiest step is a time of the day, or a date for a step of a day;
- three compact tables: the **tools** (calls with a bar of their share, errors, average time, bytes returned; the longest call is in the tooltip of the tool), the **results** (`ok`, the error codes, the refusals, with their share) and the **clients** (the name and the version that the client sent in `initialize`, its User-Agent, its requests, when it was first and last seen);
- a line says since when the usage is counted when the window starts before the counting ("Counted since ..."); a key without a request in the window says so.

Then **ClickHouse cost**, closed: what the statements of the key cost ClickHouse, read from `system.query_log` of its host (`GET /api/mcp/keys/<id>/cost`; `docs/mcp.md`, "The ClickHouse cost of a key"). It is read **only when it is opened** (a scan of the log), in the window of the usage when the cost has it (`1 h`, `6 h`, `24 h` or `7 d`: `usage.cost_windows`), else in `7 d`, and kept a minute; **Check again** reads it anew. It does not depend on the usage (`GET /api/mcp/keys/<id>/cost` answers while the usage is off): it is then the one section of the details, and, as no usage has the buttons of the window, its head has the buttons of its own (`1 h`, `6 h`, `24 h`, `7 d`, shown while it is open, `7 d` first). Six tiles (statements and failed ones, bytes and rows read, CPU, the peak of memory, the time, the bytes and rows returned), then the cost **by tool**, the **tables read** the most (a long table name ends in an ellipsis, and its title has the whole name), and the cost **by user** (the MCP user, the system user, or another user in the warning colour). When the runner of the host may not read `query_log`, the block says so and shows the `GRANT` to give (a code block with its copy button); a window too large suggests 24 h. A line says that only the statements named for the key count. When `system.top_queries` is off, the block cannot open and says why.

Each answer of the usage is kept a minute for its key and window: opening the details again shows it at once. Closing the details stops the reads in flight. Refresh forgets what was kept.

The details only show. **Delete** is the button of the row. On a phone, the details are a block under the card of the key.

## Keys that keep usage

Two kinds of key keep their usage without being in the table of the keys. The line is hidden when there is none, and **it is not there while the usage is off**.

- A **deleted key** keeps its usage until it is older than `mcp.usage.retention_days`.
- A key that **only another instance knows** (`elsewhere: true` in the answer of `GET /api/mcp/usage`) is a key made on the page of another ChDash that shares the usage directory: its usage is in the file of that instance, and this instance has no key of its name (a key that the page makes is stored by one process: `docs/mcp.md`).

Under the keys, a line opens on them: **Deleted keys** with their count, and how long their usage stays. When some of them are known to another instance only, the line says **Keys of other instances** (or **Deleted keys and keys of other instances** when there are both). The list has one line each: its name, its host, its state and its use (as the column Used). The state is the time of the deletion; the column is called **State** as soon as a key of another instance is listed (a deleted key then reads "Deleted Oct 12 08:00", and the key of another instance has the badge **other instance**, where a deleted key would have said when) and **Deleted** when the list holds deleted keys only. The table is built when the line opens. A key of the list opens its details under its line: its host, when it was deleted (or "Known to: Another instance only"), then its **Usage** and its **ClickHouse cost**, as for a key. It has no permissions, no data and no Delete. The filter and the count of the keys do not see these keys.

## The Usage tab

**Usage** (`/mcp-integration/usage`, `mcpusage.html`) is the second page of the section. It shows what **all the keys** did, over time, in six charts that it groups by key, by method, by client or by result, and cuts it by key, by method, by client, by instance, by result and by type. The usage of one key stays in the details of that key, which link here (**Open in Usage**). The page is not tied to a host. The server side is `GET /api/mcp/usage/overview` (`docs/mcp.md`). The tab has no heading row: its name is the page switcher and the row of the two pages, and the period that it covers is at the right end of the chips row.

```
Keys  [Usage]                                                                                    the nav row
[Group by . Method] [Key . All] [Method . All] [Client . All] [Result . All] [Instance . All (3)]  [1 h|6 h|24 h|7 d|30 d|90 d] (refresh)   the filter bar
[Key = ops-all x] [Method = run_query x]  Clear filters                      Oct 7 12:00 -> Oct 14 10:00   the chips (a hint without filter) and the period
[! chdash-2: its file was skipped (invalid), so its counts are not in these figures.]            the warnings (none when all is well)
[Requests] [Tool calls] [Errors] [Refused] [Call time] [Returned] [Active keys]
+--------------------------------+--------------------------------+--------------------------------+
```

- **The filters.** A filter is a value of a dimension: a key, a method, a client, an instance, a result or a type. The values of one dimension match any of them (OR). The dimensions combine (AND). Before the first answer nothing is known, and everything is offered.

The name of the check box has its count ("query_table 754"). A deleted key has the badge `deleted`; the methods of the protocol are muted. A result is its code (`ok`, `query_failed`, `rpc_error_32601`, `429_rate_limited`...) and the requests that ended with it, the successful ones too (the `count` of the `results` facet). The count is always in the last column, so that the counts of a list line up whether a row has a badge or not. An instance is a row of two lines: its name, its badge (`skipped` or `conflict` when its file is not read: its title says why) and its requests, then, under the name, a muted line that says when it wrote last (`wrote 1 min ago`, with the exact time in its title; `no write yet` when it has not written) and, for the instance that this page is, **`this instance`** (`this instance · wrote 1 min ago`). The instances are every instance that the server knows (`instances` of the answer), with zeros when one has no request in the view, in the order of the other lists (the most requests first);
  - at 20 values, the check boxes that are not ticked are off, and a line says why.

- **The tiles.** Seven: **Requests** (the tool calls, the requests of the protocol and the refused ones), **Tool calls**, **Errors** (the tool calls that ended with an error code and the requests of the protocol that failed, with their share of the requests that were read: the line says "2.73% of read requests" and the title has the whole sentence), **Refused** (the 429 and the requests that were refused before their message was read, and how many by the rate limit), **Call time** (the average and the longest time of a tool call), **Returned** (the bytes of the answers and the rows of the tools that build their own SQL: an API tool counts no row) and **Active keys** ("3 of 5 keys · 1 deleted": the keys that exist and have a request in this view, out of the keys that exist). A deleted key keeps its usage, so one that had a request in this view is counted apart, as "· N deleted" (the line has no such part when none did), and is in neither figure: "7 of 7 keys" is seven keys that exist. The server counts a deleted key with the others (`totals.active_keys`), so the page counts from the rows of the `keys` list of the answer (its facet), which have every filter but the key filter (the page applies that one): a row with requests, when the key filter is empty or has its id, is a key that exists or, with `deleted_at`, a deleted key. When the server cut that list (`omitted.keys` above 0) the rows cannot be counted, and the tile shows `totals.active_keys`, the deleted keys included, with the line "keys with requests" (no ratio, no "deleted"). Errors and Refused take the warning colour when they are not 0, and Errors the danger colour from 5% of the requests read. The sub line of a tile is one line, and a tile keeps the room of it when it has none (a time with no call, a count of rows of 0), so a row of tiles never changes its height with the filters. The longest sub lines that come ("12.3% of read requests", "12,345 by the rate limit", "of 12 keys · 3 deleted") fit the narrowest tile, 9 rem wide (seven on a line at 1100 px): the title of a tile says the rest. A count shows its digits up to a million ("1,013"). The server counts whole milliseconds, so a time of 0 reads "<1 ms". The tiles and the charts have every filter, so the bars add up to the tiles.
- **The charts.** Six charts of the shared engine, in three columns from 1280 px, two from 761 px and one below. They are cut by the same filters, so they have **the same x axis** (the steps of the window), and all of them are grouped by the Group by (key, method, client or result). **Each chart shows the 8 groups that rank first for its own metric** and adds up the others as **N more** (grey): the requests by their requests, the errors and the rate of the errors by their errors, the refused requests by their refusals, the time of a call by the tool calls and the bytes returned by their bytes. So the groups of two charts are not always the same: a method that is busy and never fails is in Requests and not in Errors, a client that is never refused is not in Refused. A group that has none of the metric of a chart is folded, even when there are fewer than 8 groups, and **N more** is left out when none of the folded groups has something to draw in that chart. When the group dimension has a filter, the groups are the values that are picked, in their order, and they are the same six in every chart. A group keeps its colour in all the charts: it comes from a hash of its name, not from its rank, so a name has the same colour in every chart, window and filter (the slots are given to all the groups that the page draws at once, and two groups never share a colour while there are no more than 18 of them: the second takes the next free one). Under its title ("Requests by method") each chart says its step: "by the minute", "by 5 minutes", "by 15 minutes", "by 3 hours", "by 12 hours" or "by the UTC day".

  **One read.** The tab reads `GET /api/mcp/usage/overview` once for one window and one set of filters (the tiles, the lists of the bar and the six charts come from it): `?window=7d&group=method&order=requests&orders=errors&orders=refused&orders=calls&orders=bytes`, then the filters. A group of the answer has a series of six figures (the requests, the errors, the refused requests, the tool calls, the time of the tool calls and the bytes). `order` (`requests`, the default, `errors`, `refused`, `calls` or `bytes`) says which figure picks the biggest groups of `series.groups`, and `orders` asks for the same groups ranked by more figures in the same read: `series.rankings` has a member for each (`errors`, `refused`, `calls`, `bytes`), a `{ groups, rest }` made as the first and on the same steps, which is what the chart of that metric draws (Requests draws `series.groups`; Errors and Error rate the ranking by errors). The server counts the cells once, and a ranking only sorts them again. A group whose figure for the ranking is 0 is in `rest`. When the Group by dimension is filtered, every ranking would be the values that are picked, in their order, so the page sends no `orders` (the answer is much smaller) and draws the six charts from `series.groups` and `series.rest`.

  **The legend** is the one of the Query chart (the shared engine, `docs/ui-foundations.md`): a **list** of the groups (a swatch and a name) and a button **Values**, which turns it into a **table** with the columns **Total**, **Min**, **Max**, **Mean** and **Last** of each group over the window (over the zoom, when there is one); **List** turns it back. The list is the default. The mode is a preference of the browser (`chdash.chart.legendMode`, the one of the Query chart), and **the six charts have the same mode**: Values on one chart is Values on all of them. The figures are those of the steps, zeros included: a group that has a request every third step has a Min of 0. The Mean of a count has up to three significant digits ("13.5", "0.0893"). **Call time** is an average, which does not add up: its table has **no Total**, and its Mean is **weighted by the calls of each step**, so it is the time of the calls of the group over their number and never the mean of the averages (a dash for a group with no call); its Min, Max and Last are those of the steps that had a call. **Error rate** is the same kind of figure: **no Total**, a Mean **weighted by the requests of each step**, so it is the errors of the group over its requests and never the mean of the rates (a dash for a group with no request), and its Min, Max and Last are those of the steps that had a request, in percent with three significant digits (`12.3%`, `1.23%`, `<0.1%`).

  A legend is the filter of the dimension of its groups (the Group by: key, method, client or result), in the list and in the table, the same in the six charts. An entry is pressed when its value is a filter, a click adds or removes the filter, and the entries that the filter leaves out dim in the six charts while the page reads. **N more** is not a filter: the lists of the bar have the keys, methods, clients and results that a chart folds, and its title says what the chart keeps ("it keeps the 8 that have the most errors"). While a filter of the Group by dimension is on, the charts list the picked values only (the server answers the values that are picked when a dimension is filtered): take the filter off to see them all. When the dimension has one value and no filter, no entry is a filter: they are disabled, with no pointer and no `aria-pressed`. The title of an entry says what the method, the client or the result is, when it stands for a group of messages or for a code that the server makes (`unread`, `invalid`, `other`, `unknown`, `ok`, `rpc_error_32601`, `429_rate_limited`...).

  **The six charts are aligned** (`alignKey` of the engine: "Alignment groups" in `docs/ui-foundations.md`). Their y axes have the same number of intervals (four, from the 156 px of the plot) and end on a step, from 0 to four steps, so **their horizontal grid lines are at the same heights** and only the numbers on them differ; they share **one left gutter**, the widest of their y labels, so **their vertical grid lines are at the same x**. The steps are 1, 2, 3, 5, 10, 20, 25, 50... for a count (whole numbers), 1, 2, 2.5, 5 x 10^n in KB, MB or GB for the bytes, 1, 2, 2.5, 5 x 10^n ms up to a second, then 1, 2, 5, 10, 15, 30 s, the same in minutes and 1, 2, 3, 6, 12 h for the time of a call, and 1, 2, 2.5, 5 x 10^n % for the rate of the errors (the `percent` kind of the engine): a rate does not pass 100%, so its axis never does either: it ends on the step above the data (0 to 4% for a rate of 3%) and at 100% when that step would go past it (a rate of 99%, or of every error code when the page is grouped by result, has four intervals of 25%: 0, 25%, 50%, 75% and 100%). The domain ends on a step, so the highest bar of a chart may stop at half of the plot: the grid lines are worth more than the room.

  **The cards keep one height**, whatever they hold, so that a filter or an answer never moves what is under them (decided 2026-10-15, on the owner's request): the head is one line, the plot is 200 px, and the legend has the room of **three lines** (four under 601 px; 20 px a line, 32 px on a touch screen) in the list mode and of **a table of six rows under its head** (four rows on a touch screen) in the Values mode, and **scrolls inside** past it (the entries stay buttons: the keyboard reaches them and scrolls the legend to them). A card with nothing to draw says so in a box of the same height. A legend that has fewer lines leaves its room empty. Only the button **Values** / **List** changes the height of the cards, the six together. Folding the rest into "N more" was not kept: the page would have to add the groups itself, and a bar whose colour is in no legend cannot be read.

  The tooltip names the step (its range, from its start to its end, or the UTC date of a day), the groups that have a value and, for a stack, the total. The cursor and a zoom (a drag; a double click resets it) go from one chart to the others. The axis of a chart by the day is labelled by dates ("Oct 9", one line: the option `xDateOnly` of the engine) and never by hours; a chart by 3 or 12 hours has ticks of days, and the charts by 15 minutes, 5 minutes and a minute keep their hours, with the date under the first one and under each midnight. When the whole window has no request, **the six cards stay** (the page does not shrink): the Requests card says "No request in the last 7 days" (with filters: "No request has all these filters", "Nothing in the last 7 days matches them." and a **Clear filters** button) and the five others say what they count, as for a figure that is 0.
- **The instances.** See "Instances": the Instance list of the bar says how many there are and what each one did last, and the warnings come above the tiles. Nothing else on the tab speaks of instances.
- **The notes.** Under the charts: since when the counting runs ("Counted since ..." when the window starts before it). The line is not there when the counting covers the whole window (the row is hidden, not empty, so the page has no blank room under the charts).
- **The address.** The whole state is in the address: `?window=7d&group=client&key=ops-all&key=ci-bot&method=run_query&client=claude-code&instance=chdash-1&result=ok&type=call` (`group` is `key`, `method`, `client` or `result`). `key`, `method`, `client`, `instance`, `result` and `type` repeat once for each value. A default stays out of it (the default window, the group by method). A change of the window, of the group or of a filter pushes an entry: Back and Forward walk through the filters. A link to the page says what it shows (the details of a key link to `/mcp-integration/usage?key=<id>&window=<window>`). The page fixes an address that it cannot use when it loads (a window that the retention does not keep, a group that the bar does not offer, the old `split`, a value that the server would refuse (an instance is 1 to 64 characters of letters, digits, `.`, `-` and `_`), a client with a space at either end, more than 20 values of a kind) with a replace, not a push. An address that has nothing to fix is left as it was written.
- **Reading.** One read of `GET /api/mcp/usage/overview` (see "The charts") when the page opens, and one for each change. A newer read cancels the ones in flight. The figures on screen stay, dimmed, until the answers come, and nothing moves while they do (the chips row, the tiles and the cards have a fixed place and height). **Refresh** reads again. There is no timer (a page at rest does no layout and no script). A page restored from the back/forward cache reads again.
- **States.** Loading: a spinner and a sentence. An error: its message and **Try again** (the bar, with the window, stays, so the reader can pick another window). A window with no request: the tiles say 0, and the cards of the charts say so (see "The charts"). MCP off: "Turn MCP on", as on the Keys page, with no bar. Usage off: "Usage is off" (below). A read that answers `404 not_enabled` (the usage was turned off after the page read the meta) ends in the same state.

### Usage is off

While `mcp.usage.enabled` is false (`usage.enabled` in `/api/mcp/meta`), nothing is counted, the three usage routes answer `404 not_enabled`, and **the page does not ask**: the Usage tab shows the shared state (`uiState.empty`) **Usage is off** and, under it, what to do:

- what the tab would show (the requests, errors, time of a call and bytes of every key over time, by key, method, client and instance) and what the details of a key would say;
- the HCL block that turns the usage on (`mcp { usage { enabled = true  dir = "/var/lib/chdash/mcp-usage" } }`, in a code block with its copy button), and a note: the directory must exist and be writable, ChDash saves its counts there once a minute in a file named for the instance, several ChDash can share the directory (the figures are then their sum), and `retention_days` says how long the counts stay.

The filter bar and the chips are not there, and the row of the two pages stays. The keys page has no column **Used** and no line of keys that keep usage; the details of a key have no usage and no **Open in Usage** link, and keep the **ClickHouse cost** (it reads `system.query_log`, not the usage). The tools of the analysis of the usage are not offered in the key form (see "Make a key").

### Instances

ChDash instances that share the directory of the usage (`mcp.usage.dir`) each write the file of their own and read the files of the others, so every answer of the usage is the **sum** of all of them (`docs/mcp.md`). Every answer says which instances it sums: `instances`, this one first, each with the time of the last write of its file and its state: `ok`, `skipped` (a file that is invalid, of another version or too large is left out, with a `reason`) or `conflict` (another ChDash writes under the name of this instance, so this one does not save its counts).

- **The note** (the keys page and the usage of a key). With two instances or more, the heading of the usage of a key says "Summed over 3 instances", and the note under the table of the keys says it too. In the heading the words are a button (`aria-haspopup="dialog"`) that opens a **popover** (`ns.popover.open`: Escape and a press outside close it, the focus goes back to the button): the instances (this one first, the others by name), each with its name, a badge when its file is not read (`skipped`, with the reason in a word, or `conflict`) and when it wrote last ("wrote 30 s ago", the time in its title). With one instance there is nothing to sum: no note. **The Usage tab has no such note** (decided 2026-10-16): it says that the usage is a sum in its Instance list (see "The Instance list").
- **The warnings.** A file that is left out of the sum is a **visible warning** (`uiState.banner`, level `warn`: amber, `role="status"`, in a box): "chdash-2: its file was skipped (invalid), so its counts are not in these figures." Several skipped files are one sentence that names the first three ("3 instance files were skipped, so their counts are not in these figures: chdash-2 (invalid), chdash-3 (too large), chdash-4 (invalid)"; a rolling upgrade of a cluster can skip dozens), and the lists of the instances (the popover of a key, the Instance list of the Usage tab) have each. A conflict is its own warning: "Another ChDash writes as chdash-0: this instance does not save its counts. Give each instance its own name (mcp.usage.instance)", with the reason of the server behind a **Why** toggle. They show above the tiles of the Usage tab, above the figures of the usage of a key and under the table of the keys, even with a single instance (a conflict is about this one). They come from the `instances` of the answer, which no filter but the instance's own changes, so they do not move while the filters do.
- **The Instance list.** The list **Instance** of the bar, the chip `Instance = chdash-1` and `?instance=chdash-1` cut the usage to one instance (or several). It follows the rule of the other lists, including "a dimension with nothing to choose is not offered": with one instance the list is off and says `Instance · chdash-0`, and nothing else on the tab speaks of instances. With **two instances or more** it is also where the tab says that the usage is a sum (decided 2026-10-16, in place of the "3 instances" note of the heading, which the tab no longer has):
  - while no instance is picked, the button reads **`Instance · All (3)`**, 3 being the number of instances of the answer (`instances`, which no filter changes), and its title says "The usage is summed over 3 instances. Pick some to see only theirs."; with a pick it reads like the other lists (`Instance · chdash-1`, `Instance · 2 selected`, the names in its title);
  - each row has what the popover of the note has: the name, **`this instance`** for the instance that this page is (`usage.instance` of `/api/mcp/meta`), the badge `skipped` or `conflict` (its title says why), when it wrote last and its requests in the view (the count of the row). The last write is a muted line under the name, `this instance · wrote 1 min ago` (the exact time in its title; `no write yet` for a file that has none), counted from the time of the answer (`format.ago`, as the popover does). The rows are in the order of the other lists, the most requests first, and not "this one first".
- **Keys of other instances.** See "Keys that keep usage".



## The secret dialog

After a create, the page shows the secret in a dialog. This is the only time. The dialog says so. It has these parts:

- the secret (a UUID), with a copy button;
- the tabs of the clients (Claude Code, Desktop, Inspector and JSON), with a copy button for each block. The Claude Code tab has the command `claude mcp add --transport http chdash-<name> <endpoint> --header "Authorization: Bearer <secret>"`.

The page builds all blocks from the real endpoint URL. The page does not store the secret. It is not in `localStorage`, in `sessionStorage` or in the address. When the dialog closes, ChDash removes the dialog and its nodes from the page. The keys table shows only the hint and dots (with the hyphens).

| Action | Confirmation | Result |
| --- | --- | --- |
| Delete | Yes (the focus starts on Cancel) | The key is removed. Its clients get `401` at once. This cannot be undone. |

## Keyboard and accessibility

- Every control is a button, a link or a form field. The dialogs trap the focus and give it back when they close.
- Each field has a label. Each group (hosts, permissions) has a legend. An error is a live region, and its field has `aria-invalid`. The arrow of a family is a button with `aria-expanded` and `aria-controls`.
- Row action buttons have a label that names the key ("Delete ci-bot"). The Delete button wears the danger color at rest, so touch users see it too.
- The Usage tab: a chip has a remove button with a label ("Remove filter Key = ci-bot"), and the keyboard moves on to the next chip when one goes. A legend entry, in the list and in the table, is a button with `aria-pressed`; one that is not a filter ("N more", or any entry when the dimension has one value) is disabled and has none. The table of a legend has a label, a scope on each header and a header on each row, and the button **Values** / **List** has `aria-pressed`. The six charts are sections named by their headings (`h3`, under the `h2` of the part and the `h1` of the page, which are for screen readers only), each a group named for what it draws ("Requests by method over time"). A change says what it found, once, in the live region of the page ("1,012 requests in the last 7 days with these filters.").
- The lists of the filter bar: the button has `aria-haspopup="dialog"`, `aria-expanded` and `aria-controls`; Down or Up on it opens the list on its first control, Down and Up move between the controls (the action, then the check boxes), Space ticks a box, and Escape closes the list and gives the focus back to the button. The name of a check box is its value and its count (for an instance, also its badge and when it wrote last). The field that narrows a long list has a label of its own. A list that has nothing to choose from is `disabled` (and `aria-disabled`), and its title says why. Group by is a list of one choice (a listbox) with its name. axe finds nothing on the bar, with a list open, in both themes.
- The instances: the note of the usage of a key ("Summed over 3 instances") is a button with `aria-haspopup="dialog"` and `aria-expanded`; its popover is a dialog with a name (`Instances of the usage`) that takes the focus, Escape closes it and gives the focus back to the button. On the Usage tab the instances are the rows of the Instance list, a dialog of check boxes like the others: the name of a check box is the instance, its requests and its last write ("chdash-1 2,701 wrote 1 min ago"), and its badge (`skipped`, `conflict`) is read with it. A warning about an instance is a notice (`role="status"`), not an alert: it does not interrupt. The state "Usage is off" has a name (`aria-label`) and its code block has its copy button.
- The key form: a tool that every key has is a check box that is checked and `disabled`, and "Every key has it" is part of its label; a tool that "*" does not give is a check box with `"*" does not include it` in its label. axe finds nothing on the form, the note with its popover open, the warnings or "Usage is off", in both themes.
- The page works at 390 px without a horizontal scroll. Code blocks scroll inside themselves. The table of a legend that is wider than its box scrolls in it.
- The page uses the design tokens only. It follows the dark and light themes.
- The document does not scroll. The panel scrolls and the header stays.

## Decisions

- The page has no visible title and no strip. The page switcher names the page, as on System. The endpoint is in the side column, where a client needs it, and New key is in the heading of the keys, where the keys are.
- A key is one line, and its name column is narrow. A name has 32 characters at most, so the room goes to the side column, which holds the commands of the clients.
- The secret shows its start only (`3f2a9c1e-••••…`, decided 2026-10-14): the hint tells the keys apart, the whole mask is in the tooltip, and the column Used fits beside the others without a column that leaves at some widths.
- The use of a key shows in the table and in its details (decided 2026-10-14): the column says which keys are used and how much, the details say how. The column is one request for every key, for a fixed window (7 days); the details pick their window. The last use comes from the usage of the key, which is kept in files and survives a restart. A key that the counting does not cover since its creation is a dash, not "Never".
- The usage of all the keys is a page of its own, **Usage** (decided 2026-10-15). On 2026-10-14 the owner had set a global view aside; the next day he asked for one, on the model of the usage page of Helius: tiles, bars over time that one dimension stacks, filters that are chips, a window. It answers "how is MCP used?": by which keys, which methods, with which results, over time. It is a second page of the section, with a row of two links as System has its sections, because the keys page is full and the charts need the room.
- Every dimension of the Usage tab filters every other (decided 2026-10-15). The questions are crossings ("which method fails for this key?", "which key is refused?"), so the server keeps the cells (type, client, method, result) of each key for each step, and every filter combines with the others. A list of the bar has every filter but its own, so that it lists what else can be picked.
- The clients are a dimension of the window like the others (decided 2026-10-15, the same day as the tab: the first version kept them for life, with the key filter only, and the owner asked for them to be grouped and filtered by). A client is named by what it says (its `clientInfo` name, else the product of its User-Agent), so the cells can count by name and an update of a client does not break a series; its versions and its last sight still come from the clients that each key keeps for life.
- The tab has charts over time, a Group by and a filter bar at the top (decided 2026-10-15, on the owner's request, with four charts; two more came on 2026-10-16, below): the requests alone did not say how the keys fail (errors), how long they wait (call time) or what they cost the network (bytes returned). The charts share their axis, their groups and their colours, so that one group is read across them. Group by was Key, Method or Client at first: the result and the type are things that happen to a request, not who asks or what it asks, so they stayed filters (the result became a Group by on 2026-10-16: see below; a link carries a type). The bar is the one of Observability and System, with the lists of check boxes of the Service list of Logs, so that a filter is made in one place, whichever page it is.
- A filter never moves the page (decided 2026-10-15, on the owner's request). The chips row appeared with the first filter and went with the last, and the legends gained and lost lines, so the tiles, the charts and the tables jumped under the pointer at each click. The row is always there (a hint says so), one line high; the cards have one height (a legend of three lines that scrolls past them); an empty chart has the height of a chart; a tile keeps the room of its sub line. The cost is some blank room under a short legend and a hint line when there is no filter; the gain is that the next click is where the last one was. The chips never wrap: a second line of chips would be a second height. A sideways row with a fade is how the shell shows a row that does not fit (the tab rows, the trace highlights).
- A dimension with nothing to choose is not offered (decided 2026-10-15, on the owner's request). A list with one value, a row that picks the only client and a legend entry that filters by the only key cut nothing: the click changes the address and reads the usage again for the same figures. The page says what the one value is (`Client · claude-code`) and keeps the place of the control, so that the bar does not change its shape. A filter that is on keeps the dimension offered, so that it can be taken off. The facet decides: it has every filter but its own, so it is what could be picked.
- Each window has a step of its own, from a minute to a day (decided 2026-10-15): the owner wanted to watch the last hour minute by minute and the last 90 days by the day. The server keeps one tier for each step and the page never adds steps up, so a figure of the page is a figure of the server. The call time is an average, which does not add up: the legend gives the time of the calls over their number, and a step with no call is a gap.
- The "methods" are the tools and the methods of the MCP protocol (decided 2026-10-15): a fixed vocabulary, so that a client cannot fill the memory with names (a method that is not in it counts as `other`, one that cannot be read as `invalid`, a request that was refused before its message was read as `unread`).
- The chart colours a group by a hash of its name, not by its rank. A rank changes with every window and every filter, and a person who follows "ping" from 7 days to 24 hours would lose it. The groups that the page draws never share a colour (up to 18 of them), and the charts do not draw the same groups, so the slots are given to all of them at once: a group has one colour in the six charts.
- A legend entry, a list of the bar and a chip are three ways to one filter. The charts are the first thing that the reader sees, so their legends have to filter; the lists of the bar are where a value is picked from the top, without looking for it (and where the groups that the charts fold into "N more" are found); the Values table of a legend lists the figures of each group; the chips say what is on, and remove it.
- Six charts and no tables (decided 2026-10-16, on the owner's request). The four tables (by key, method, result and client) said again what the lists of the bar and the legends said, and took the room of the page; their figures are now the Values table of the legend of each chart. The result, which only a table could pick, was picked in the legend of a new chart, **Errors by code**, which said what the errors are (the code) and not only how many (the chart was replaced on 2026-10-16: see below). **Refused** is a chart of its own because a refusal (429, 413...) is the sign of a client that is too busy or too large, not the failure of a tool, and the errors do not count it. The server gained the series `refused` and the parameter `order` (the biggest groups by a metric) for them. The cost: there is no table to read the figures of the 200 values of a facet: the lists of the bar have the counts.
- The result is a Group by and a list of the bar, and each chart ranks by its own metric (decided 2026-10-16, on the owner's request). **Errors by code** needed a second read (the page grouped by result), a legend that filtered another dimension than the five others, and a result that could be picked nowhere else. The owner's choice was to make the result a dimension like the key, the method and the client: the fourth entry of the **Group by** (`group=result`) and a list of the bar, **Result · All**, between Client and Instance. Every chart follows the Group by, so the error codes show in Requests, Errors and the others when the page is grouped by result. The place of the chart is now **Error rate**, which says how bad the errors are where Errors says how many (its axis is in percent, and the engine gained the `percent` kind for it). And each chart shows the 8 groups that rank first for **its own** metric: Errors would otherwise show the busiest methods, most of which never fail. The server ranks the groups once for each metric in the read of the page (`orders`, `series.rankings`: the cells are counted once, which is why one read was enough). The cost: the bar has six pickers (the Group by and the Instance list have more room than the other four, so that no word is cut at 1101 px), the charts do not draw the same groups (so the colours are given to all of them at once, and a legend says what its chart keeps), and grouped by result the rate is 100% for every error code (all the requests of an error code are errors) and 0% for the others.
- The legend is the one of the Query chart (decided 2026-10-16). One component for every chart: a list that costs a line or two, and a table of the figures for the reader who wants them (the Total column was added to it for every chart, the Query chart included). The list is the default because the reader looks at the shapes first; the mode is one preference, so the six charts that are read side by side are read the same way. A chart of an average has no Total (a sum of averages means nothing) and weighs its Mean by the calls of each step, so the figure is the same as the tile's; the rate of the errors is read the same way, weighed by the requests. The figures read the steps with their zeros, so a minimum of 0 says that the group had quiet steps.
- The charts are aligned (decided 2026-10-16, on the owner's request). Six charts that are read across and down should be read across and down: their grid lines are on the same lines, so a peak is compared with the line, not with a number. It is the engine's `alignKey` (not a layout of this page), so any page can opt in with one option. The cost is that a step is a "nice" number and the domain ends on it, so the highest bar of a chart may reach only half of the plot, and that the gutter of every chart is as wide as the widest label.
- The ClickHouse cost of a key is read only when its block is opened: it scans `system.query_log` of the host. The usage, counted by ChDash, is read when the details open.
- A deleted key keeps its usage, and its line opens on it under the keys, so a key that leaked and was deleted can still be looked at. It is not a row of the keys table: its secret, tools, data and limits mean nothing, and the filter and the count stay about the keys that exist.
- A key is made or deleted, never changed. An edit form, a switch and a rotation were three more things to build, explain and test for a key that costs one click to make again. To change a key, delete it and make a new one.
- A key has no description and no expiry. A description was text that nobody read, and an expiry was a state that the page had to explain. Delete a key that you do not use any more.
- A secret shows once, and ChDash keeps only its hash. A page that could show every secret again gave all the durable credentials to anyone who could reach the page (or to a site that tricked a browser into calling it). The cost is that a lost secret means a new key, which is one click (`docs/mcp.md`, "Secrets and the key file").
- A key reads one host. A key with several hosts made a client guess which MCP user answers, and a tool call had to name its host. One key for each host: the name of the key says which, and every tool call uses it. There is no "All hosts" and no "All data" choice: the data is a list of patterns where `*` is everything. One way to say a thing.
- A tool that the MCP user of the host cannot serve cannot be given. A key that promised it would fail on every call, and the person who made the key would learn it from a client.
- A permission has two states, so it is a check box. A select with "No access" and "Read-only" asked for a click to open and a click to choose, for the same information.
- The families are not known by the page. With more than 60 tools, a flat list would not fit a dialog and would need a change of the page for each new tool. A family is a row of the server's table; a tool is a row of the API tool table. The page draws what `/api/mcp/meta` sends.
- The source of a key shows as a lock on the keys that the page cannot delete. A `config` badge on every row repeated the same word.
- A page opened with MCP off shows the HCL block and does not redirect. This helps an operator who follows a link.
- The client-side server name is `chdash-<key name>`, so two keys do not collide in a client.
- Delete asks for confirmation: it is destructive.
- The HCL block of the "MCP disabled" state shows `mcp_uri` with the password inside the URI. The MCP user has no separate password setting (see `docs/mcp.md`).
- Usage is a state, not an error (decided 2026-10-15, with the switch of `mcp.usage.enabled`). With the usage off, nothing is counted, so the Usage tab has nothing to show and says how to turn it on, and the keys page loses what only the usage gave it (the column Used, the keys that keep usage, the usage of a key). The ClickHouse cost of a key stays, because it reads `system.query_log` and not the usage, and gets the buttons of its window, which the usage had held. The page does not ask a route that is off (it would answer 404 `not_enabled`).
- Instances are a filter, not a grouping (decided 2026-10-15, on the owner's request, when the usage became one file for each instance). The reader who has several ChDash behind a balancer asks "is it one node?", which is a cut of the figures, so the instance is a list of the bar and a chip; the charts keep to key, method, client and result. The same rule applies as for the others: a list with nothing to choose is off, and says the one value.
- A figure that is a sum says so, and a file that is left out says why (decided 2026-10-15). The sum of several files is silently wrong when one of them is missing, so the Instance list of the Usage tab (`Instance · All (3)`) and the heading of the usage of a key ("Summed over 3 instances") name the instances that they sum, and a skipped file or a conflict is a warning above the figures, with its reason, instead of a number that is a little low.
- The tools of the analysis are drawn from the catalog, by their flags and not by their names (decided 2026-10-15). The tools that every key has are checked and locked, so that the form shows what a key will hold and never sends it; the tool that gives the usage of all the keys is named by hand, off by default, and "*" does not include it, since it shows the names, hosts and clients of the other keys to the client's model; a tool that the server does not offer now is not shown.
- The Usage tab has no heading row (decided 2026-10-16, on the owner's request). The row said "Usage of all keys" (the page already has its name: the page switcher and the row of the two pages), the dates of the window and "3 instances", and it took a line of room above the figures. The dates are the period that the figures cover, which belongs with the filters that cut them, so they went to the right end of the chips row (a line that is already always there, so the page does not move). The instances are a cut of the figures too, and the Instance list is where they are picked: it says how many there are (`Instance · All (3)`) and what each one did last, so the tab needs no note and no popover of its own. With one instance the tab says nothing of instances. The note about the rows (an API tool counts no row) went too: the tile of the bytes explains it in its title. The heading stays for screen readers (an `h2`, `srOnly`), since the titles of the charts are `h3` and a level of heading must not be skipped.
